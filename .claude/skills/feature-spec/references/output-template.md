# Output templates

Three shapes: `spec.md` (full feature), `impact.md` (full feature), and the thin-feature note.
Gate criteria are in [gates.md](gates.md); the Step block shape is in
[plan-step-template.md](plan-step-template.md). IDs are `BR-01`, `TS-01`, `AC-01`, `E2E-01`,
unique within the feature folder. No file name or placeholder carries a date; the date lives in
the header.

## `docs/features/<slug>/spec.md`

```markdown
# <Feature Title> — Feature Specification

> Generated by `/feature-spec`. Source of truth: [story.md](story.md). Impact: [impact.md](impact.md).

|                  |                                                                   |
| ---------------- | ----------------------------------------------------------------- |
| Feature          | <title>                                                           |
| Version          | 0.1.0                                                             |
| Spec source      | `docs/features/<slug>/story.md`                                   |
| Standing context | OVERVIEW §1–3 (path per `.claude/repo-profile.md` § Feature docs) |
| Domain entry     | <domain file, or the fallback in use>                             |
| Behavioral gate  | <e2e runner and spec file> — see `.claude/repo-profile.md`        |
| Date             | <today, ISO 8601>                                                 |

## Gate summary

| Gate            | Phase                   | Role  | Result |
| --------------- | ----------------------- | ----- | ------ |
| G0 Scope        | Scope & inputs          | —     | PASSED |
| G1 Business     | Business analysis       | BA    | PASSED |
| G2 Discovery    | Discovery               | —     | PASSED |
| G3 Impact       | Impact analysis         | SA    | PASSED |
| G4 Design       | Technical specification | SA    | PASSED |
| G5 Acceptance   | BDD acceptance criteria | BA    | PASSED |
| G6 Verification | Verification mapping    | SA    | PASSED |

| G-Exec          | Implementation plan     | SA    | PASSED |
| G9 Challenge    | Contrarian review       | BA↔SA | PASSED |
| G10 Review      | Independent review      | —     | PASSED |

_(Use `PASSED WITH OPEN ITEMS` where applicable, linking to Open Questions.)_

Each flagged `[in spec]` or `[derived]`.
### 1.6 Out of scope

## 2. Technical specification — SA

### 2.1 Approach
### 2.2 Design elements
`TS-` | Element | Satisfies `BR-` | Impact entry (file path from impact.md)
### 2.3 Data model
Concrete types (in the repo's own language) for anything persisted or passed between modules.
### 2.4 Module map
Files to add or change, one line of responsibility each — consistent with impact.md.
### 2.5 Dependencies
Earlier features this builds on, each marked built (commit) or unbuilt.
### 2.6 Non-functional notes

Each decision with the reason. Section 8 Steps cite these instead of re-deciding.
### 2.8 Do not touch
Paths and behaviors out of bounds, with the reason. Includes every `don't-touch` in impact.md.

## 3. BDD acceptance criteria — BA
`# AC-01` comment before each scenario, in a `gherkin` block.

## 4. Verification mapping — SA
`E2E-` | AC | Method (`e2e`, `compiler` or `manual`) | Steps | Assertion

ACs; TS in no Step; E2E in no Step. All empty.
```

## `docs/features/<slug>/impact.md`

```markdown
# <Feature Title> — Impact Analysis

> Generated by `/feature-spec` Phase 3. Date: <today, ISO 8601>. Spec: [spec.md](spec.md).

## Domain map (Phase 2 result)

Domain: <name> — entry point: <domain file or fallback>

| Item | Status (`exists` / `missing`) | Evidence |
| ---- | ----------------------------- | -------- |

Unbuilt dependencies: <feature or module, with evidence it has not landed — or "none">

## Impact entries

| Path | Class | Verified | Callers affected | Shared state | Migration risk | Why |
| ---- | ----- | -------- | ---------------- | ------------ | -------------- | --- |

`Class` is `add`, `change`, `read-only` or `don't-touch`. `Verified` shows how existence was
checked (`git ls-files`, opened file) — for an `add` entry, that the path is free.

## Safety facts (blast radius)

Per `references/blast-radius.md`. Skipped entries: <path — reason, or "none">.

| Change | Safety fact | Level reached (1–5) | Proof |
| ------ | ----------- | ------------------- | ----- |

**Risks** — how it breaks, `file:line`, likelihood × cost, how to check, and where it is carried
(`TS-` / Decision / Open Question).

**Cleared** — what was checked and why it's fine.

**Before merge** — the cheapest check that catches the real bug, an e2e test wherever one can observe it (becomes an `E2E-` row).
```

## Thin-feature note

For a story with ≤2 Gherkin scenarios and no new storage key or module boundary. Written to
`docs/features/<slug>/spec.md`; no `impact.md`, no reviewer round. Keep it short.

```markdown
# <Feature Title> — Thin Spec

> Generated by `/feature-spec`. Source: [story.md](story.md). Date: <today, ISO 8601>.

## Purpose
<one paragraph>

## Business rules
- BR-01 — <rule> (source: <Gherkin line / OVERVIEW bullet>)
- BR-02 — <rule>

## Module map
| Path | add / change | Responsibility |
| ---- | ------------ | -------------- |

## Impact
<2–5 lines: callers affected, shared state, migration risk, anything `don't-touch`. Every
`change` path verified to exist.>

## Verification
| E2E ID | BR | Method | Steps | Assertion |
| ------ | -- | ------ | ----- | --------- |
| E2E-01 | BR-02 | e2e | <entry point, fixture, actions> | <expectation> |

## Implementation order
1. <step> — satisfies BR-01 — Verify: `<typecheck command>` → exits 0
2. <step>; add the e2e spec file with E2E-01 — satisfies BR-02 — Verify:
   `<single-test e2e command> "E2E-01"` → passes
```

Every runtime rule gets an `e2e` row, as in a full spec. Two to four steps, each with a
Verify command or concrete manual step. `/sdd` executes this list
the way it executes Section 8.
