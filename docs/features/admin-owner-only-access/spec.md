## 1. Business analysis — BA

### 1.1 Purpose

The portfolio's content will live in a Cloud Firestore database that the browser talks to directly, because the site has no server. The only thing that stops a stranger from defacing it is the database's own access rules. This feature writes those rules so that only the owner's Google account can change content, so that a draft blog post is readable by the owner alone, and so that, until the owner has filled in their Firebase user ID, nobody can change anything. It also gives the owner, at that stage, a plain notice on the panel that saving is not switched on yet, with their own user ID and the steps to switch it on. It builds no editor and no read of the database by the panel.

### 1.2 Actors & preconditions

- **Visitor (signed out):** anyone who sends a request to the database.
- **Owner:** the site owner's single Google account, identified by Firebase user ID, never by email (story Assumption 1).
- **Other account:** any other signed-in Google account.
- Precondition for "switched on": the owner has put their user ID in the database rules **and** in the panel's owner constant, and the rules have been deployed (story Assumptions 1 and 13; intent §7).
- The Firestore database, the Google sign-in provider and the Rules Admin role for the deploy account are created or granted by the owner in the Firebase console (intent §7); no automated check depends on them.

## 2. Technical specification — SA

### 2.1 Approach

A new `firestore.rules` file holds the security boundary: one function names the owner by user ID (a placeholder string until the owner fills it in), the five plain content collections are public to read and owner-only to write, `blogPosts` is public to read only while a post's `draft` flag is `false` and owner-only to write, and everything else is refused by default. `firebase.json` points Firestore at that file and configures a Firestore emulator on `127.0.0.1:8080`; Playwright's emulator command starts Auth and Firestore together. The new spec drives the emulator directly over its REST endpoints: it creates accounts in the Auth emulator, loads the repo's rules text with the owner placeholder replaced by an account's real user ID (or verbatim for the placeholder state), seeds documents with the emulator's admin bypass, and sends writes and reads with and without an ID token, so no browser, Google account or live project is involved. The live deploy job gains a rules deploy that runs after the hosting deploy. The panel gains one small component, shown on the allowed screen only while the owner ID is unfilled. No Firestore client code is added.

### 2.6 Non-functional notes

- Static export holds: no client Firestore code, no new import in any page or bundle, `hosting` untouched (CLAUDE.md Invariants 1, 2).
- The notice is styled with the existing tokens only (`--surface-alt`, `--foreground`, `--muted`, `--border`), no raw colours and no Tailwind `dark:` variant (CLAUDE.md "Never violate").
- The Firestore emulator needs Java (Java 21 is installed; the emulator jar is cached in `~/.cache/firebase/emulators/`). CI runs no e2e, so CI needs no Java.
- Rules are project-wide, not per hosting channel (impact.md): only the production job deploys them.
- Internal admin panel for one owner: no rate limits, no field validation in the rules, no audit trail (story Out of Scope).
