## 1. Business analysis — BA

### 1.1 Purpose

The site owner needs a private page, at an address nobody is told about, where signing in with their own Google account opens a menu of the six content sections. Anyone else who finds the address sees only a sign-in control, or, if they sign in with another Google account, a message that the account is not allowed. This slice builds the sign-in shell and nothing behind it: no editor, no save, no database read. It also carries the new tooling (the Firebase client library, the local sign-in stand-in) that the later slices rely on.

### 1.2 Actors & preconditions

- **Visitor (signed out):** anyone who opens the panel's address.
- **Owner:** the site owner, signed in with their Google account. Identified by Firebase user ID, never by email (story Assumption 1).
- **Other account:** any other signed-in Google account.
- Precondition for "other account": the owner's user ID has been filled in (story Scenario 3). Until then nobody can be told apart from the owner (Assumption 2).
- The Google sign-in provider and the allowed sign-in domains are switched on in the Firebase console by the owner (intent §7); the automated checks never depend on that (Assumption 9).

## 2. Technical specification — SA

### 2.1 Approach

A new static page at `src/app/bright-warm-greenhouse/page.tsx` carries `noindex` metadata and renders one client component, `AdminPanel`, which owns every sign-in screen. The page and `AdminPanel` are the only importers of a new client-only module group, `src/lib/firebase/` (committed web config, a lazily created Firebase app and auth, and four small auth helpers), so the Firebase library ships in the panel's own chunks and in no public page. Who counts as the owner is a pure function of two user IDs in `src/lib/admin/owner.ts`, with a placeholder constant until the owner fills it in. The panel talks to Google in production and to the local Auth emulator on `127.0.0.1` and `localhost`; `firebase.json` gains the emulator entry and Playwright starts it beside the static server, so the feature's own Playwright spec drives a real popup flow against the stand-in. No database is read.

### 2.3 Data model

Nothing persisted by this repo's code.

```ts
// src/lib/firebase/auth.ts
export type AdminUser = { uid: string };

// src/lib/admin/owner.ts
export type AccessState = "unfilled" | "owner" | "not-allowed";

// src/lib/admin/sections.ts

  | { kind: "loading" }
```

Browser storage touched: the Firebase library's own sign-in session (IndexedDB, written by the SDK) and, on local hosts only, a read of `localStorage["admin.ownerUid"]`.

### 2.5 Dependencies

No earlier feature: this is slice 1 (unbuilt dependencies: none). New packages (approved, intent §4): `firebase` (known good at spec time: 13.4.0, whose `firebase/auth` and `firebase/app` import cleanly in Node 22) and `firebase-tools` (dev; known good 15.37.0, needs Node >= 20; the machine runs 22.23.5).

### 2.6 Non-functional notes

- Static export holds: the page is prerendered; the Firebase app and auth are created only in effects and event handlers, never at module load or during render, so `next build` never calls them.
- The public pages must load none of the library; E2E-13 proves it on the built output.
- The Auth emulator needs no Java (only the Firestore and Storage emulators of later slices do).
- Bundle weight: the Firebase auth library loads on the panel page only (intent §4).

## 3. BDD acceptance criteria — BA

```gherkin
# AC-01
Scenario: Signed-out visitor opens the panel address
  Given nobody is signed in
  When the visitor opens "/bright-warm-greenhouse/"
  Then the visitor sees a "Sign in with Google" control

  And the page shows none of the portfolio's content

Scenario: Owner signs in after the owner's user ID is filled in
  Given the owner's user ID is filled in with the signed-in account's user ID
```
