## 1. Business analysis — BA

### 1.1 Purpose

The owner wants to write and fix blog posts without opening the code or making a commit. Choosing "Blog posts" in the admin menu shows the saved posts, newest date first, each with its title, slug, date and a status written as text, and lets the owner add a post, edit it and delete it after confirming. A post has a title, excerpt, date, slug, tags, a cover image with its alt text, a markdown body, a "Featured" setting and a status of Draft or Published: the fields the blog's markdown files carry today. The slug is the post's identity: it is typed once when the post is added, never changes, and a save that would reuse an existing slug is refused and overwrites nothing, even from a second tab. The cover image is either an uploaded image chosen from the image library or a repo path typed as text, one source at a time (the pattern Certifications uses). A Draft post is stored so that the database rules show it to the owner only; this slice sets and shows the status and the rules (already built) enforce it. Nothing is prefilled from the repo's markdown files, the public blog still renders from `content/blog/*.md` (phase 2), and the rendered preview is the next slice.

### 1.2 Actors & preconditions

- **Owner:** the single Google account whose user ID is in the rules and in the panel's owner constant. Saving, editing and deleting work only for them once the ID is filled in.
- **Unfilled owner:** signed in while the user ID is still the placeholder. The panel shows the saving-off notice. Because a list read of `blogPosts` needs the owner (drafts are hidden from everyone else), the list cannot load for this account and the editor shows the shared load failure; no write is possible.
- **Other account / visitor:** never see the editor; `admin-sign-in` and `admin-owner-only-access` cover them, and the editor is rendered only on the allowed screen.
- Preconditions met by hand (intent §7): the owner's user ID in the rules and the panel constant. No automated row depends on them; every row runs against the local emulators.

### 1.4 Data touched

Two collections of the database. `blogPosts`: one document per post, its id the slug, holding the title, excerpt, date text, tags list, the draft flag, the Featured flag, the cover (an uploaded image's public address or a repo path, in one text), the cover alt text, the markdown body, the creation time and the last-write time. The editor reads the whole collection (owner only, by the rules), creates a document if its id is free, updates the content fields of one and deletes one. `images`: read only, to list the uploaded images by name for the chooser (owner-only by the rules, written by the image library, never written here). It reads nothing from the signed-in account and uses no browser storage.

## 2. Technical specification — SA

### 2.1 Approach

The shared list editor does most of the work; this slice adds a pure module, a dedicated store and a thin editor, and gives `ListEditor` the three optional props the blog needs. `src/lib/admin/blogposts.ts` is pure (types, texts, check, tolerant read, the status-to-`draft` mapping, ordering and the row lines). Blog posts are keyed by slug and added create-only, which the generic position-based list store cannot do, so `src/lib/firebase/blogposts.ts` is a small dedicated store that still implements the shared `ListStore<BlogPostContent>` interface: `add` is a transaction that reads `blogPosts/<slug>` and writes only if it is missing, `update` and `remove` are single writes under the shared 10-second timeout (`withTimeout`, now exported from `list.ts`), and `load` reads the whole collection and sorts it newest date first. `ListEditor` gains `movable` (hide the move buttons), `order` (the sort applied after an add and an edit) and `saveFailure` (turn a thrown error into the shown message, used for "A post with this slug already exists"); with the three absent the four existing editors behave as today. `BlogPostsEditor.tsx` loads the uploaded images once (the Certifications pattern), keeps the cover as one string matched back to an image by the existing `photoSelection`, and renders `ListEditor` with the blog fields. `AdminPanel` renders it for "Blog posts" and drops the placeholder branch, since no menu item is left without an editor. The rules need no change: `firestore.rules` already lets the owner write `blogPosts/{slug}` and hides drafts from everyone else, so the only thing the panel owes the rules is writing `draft` as a boolean on every save. Six earlier tests that expect the "Blog posts" placeholder move to the editor's heading, in their own Step.

### 2.3 Data model

```ts
// src/lib/admin/blogposts.ts (pure: no firebase, no window)
export const BLOG_POSTS_COLLECTION: string;            // "blogPosts"
export type BlogStatus = "Draft" | "Published";
export type BlogPostContent = {
  title: string;
  excerpt: string;
  date: string;        // "YYYY-MM-DD" text, the blog's own format
  slug: string;        // the post's identity; equals the document id
  tags: string;        // comma-separated text in the form; stored as a list
  coverImage: string;  // an uploaded image's public address, or a repo path, or ""
  coverAlt: string;
  body: string;        // markdown, exactly as typed
  featured: boolean;
  status: BlogStatus;  // stored as `draft`
};
```

Firestore: collection `blogPosts`, one document per post, **document id = slug**, fields exactly `title`, `excerpt`, `date` (strings), `tags` (array of strings, `[]` when none), `draft` (boolean, always written), `featured` (boolean), `coverImage`, `coverAlt`, `body` (strings, `""` when empty), `createdAt` and `updatedAt` (numbers, `Date.now()` milliseconds; a new post gets the same value in both, an edit rewrites `updatedAt` only). The names are those of `BlogFrontmatter` (`src/lib/blog/types.ts`) plus `body`, so phase 2 can read the same fields; `updated` and `readingTime` are not stored (story Deferred and Assumption 9). `draft` is `true` for status Draft and `false` for status Published. The uploaded images are read from `images` through the existing `listImages()` and never written.

### 2.6 Non-functional notes

- Static export holds: no server, route or generated param is added; the editor is a client component reached only through `AdminPanel`, and Firestore is touched only inside effects and handlers.
- Public pages stay Firebase-free (E2E-23). Invariant 3: no file in this feature imports the `@/lib/blog` barrel, `src/lib/blog/posts.ts` or `server-only`; the pure module imports `formatDate` from `../blog/types` only. Invariant 4: every date shown goes through `formatDate` (UTC).
- Internal admin panel for one owner: no autosave, no draft of the form, no conflict check on an edit, no field-length limit, no pagination; long text wraps. A body past the database's document size limit fails to save with the shared failure message.
- Tokens only for colour (the ones `formParts.tsx` already uses); no `<img>`, no `next/image`, no thumbnail.
- Accessibility: every control is a native input, textarea, select, checkbox or button reached by keyboard; each error is linked to its field with `aria-describedby`; the status is text, not colour.
- No `eslint-disable` or `@ts-ignore` line is added anywhere; the new component sets state only after an `await` in its image-loading effect (the Certifications editor's shape), never synchronously.
- None of the new files holds the word `email` (`admin-sign-in` E2E-15 searches every admin source except the three profile files for it).
