## 1. Business analysis — BA

### 1.1 Purpose

The owner wants to keep the list of certifications current without opening the code. Choosing "Certifications" in the admin menu shows the saved certifications in saved order and lets the owner add one, edit it, move it up or down one place, and delete it after confirming. A certification has three fields, all required: a name, a badge image and a credential link. The badge is either an image chosen from the owner's uploaded images (the image library) or a repo path typed as text, one source at a time, the same pattern the Profile photo uses. Nothing is prefilled from today's site, so the first time the list is empty. This screen reuses the list editor built by `manage-experience` and extended by `manage-projects`; the list, the form shell with Save and Cancel, Move up and Move down, the in-row delete confirmation, the messages and the busy guard are shared, and this slice only says what a certification's fields are. It does not change what visitors see (phase 2).

### 1.2 Actors & preconditions

- **Owner:** the single Google account whose user ID is in the rules and in the panel's owner constant. Saving, moving and deleting work only for them once the ID is filled in.
- **Unfilled owner:** signed in while the user ID is still the placeholder; the panel shows the saving-off notice, the list loads (`certifications` is publicly readable), the uploaded-image list does not (`images` is owner-only) and every write is refused by the rules.
- **Other account / visitor:** never see the editor; `admin-sign-in` and `admin-owner-only-access` cover them, and the editor is rendered only on the allowed screen.
- Preconditions met by hand (intent §7): the owner's user ID in the rules and the panel constant. No automated row depends on them; every row runs against the local emulators.

### 1.4 Data touched

Two collections of the database. `certifications`: one document per certification holding the name, the badge (an uploaded image's public address or a repo path, in one text), the credential link, the certification's place in the list (`position`, a number) and the time of the last write. The editor reads the whole collection (publicly readable by the rules), adds a document, updates the content fields of one, updates only the place of the certifications a move changes, and deletes one. `images`: read only, to list the uploaded images by name for the chooser (owner-only by the rules, written by the image library, never written here). It reads nothing from the signed-in account and uses no browser storage.

## 2. Technical specification — SA

### 2.1 Approach

The shared list editor does the work; this slice adds the usual three-file configuration plus the one small thing the story forces. `src/lib/admin/certifications.ts` is pure (types, texts, check, tolerant read, label). `src/lib/firebase/certifications.ts` is one line binding `createListStore` to the `certifications` collection. `CertificationsEditor.tsx` loads the uploaded-image list once (the Profile editor's pattern) and renders `ListEditor` with the Certifications fields: Name, a Badge image group (an "Uploaded image" chooser and a "Badge image path" input, one value stored in `icon`, matched back to an image by the existing pure `photoSelection`) and Credential link. The story names the control "Add certification" where `ListEditor` says "Add entry", so `ListEditor` gains one more optional prop, `addLabel`, whose default keeps Experience and Projects exactly as they are; the other three optional props (`emptyText`, `listLabel`, `newPosition`) already exist from `manage-projects` and are only passed. `AdminPanel` renders the editor for the "Certifications" item on the allowed screen only. The rules need no change: `firestore.rules` already lets anyone read and only the owner write `certifications/{id}`. Four earlier tests that used "Certifications" as the example placeholder move to "Tech stack". The rows are pure (`certifications.ts`) and screen rows for the seven scenarios, the badge-source rules, the menu and the public pages; shared behaviour already proved is re-run, not copied.

### 2.3 Data model

```ts
// src/lib/admin/certifications.ts (pure: no firebase, no window)
export const CERTIFICATIONS_COLLECTION: string;                    // "certifications"
export type CertificationContent = {
  name: string;
  icon: string;   // the badge: an uploaded image's public address, or a repo path, or ""
  url: string;    // the credential link
};
```

Firestore: collection `certifications`, one document per certification, a new unique string id, fields exactly `name`, `icon`, `url` (strings), `position` (a number, integer valued) and `updatedAt` (`Date.now()` at the last write, milliseconds). The names are the public component's own (`src/app/components/certifications.tsx`: `name`, `icon`, `url`), so phase 2 reads the same fields. Order, ties and the missing-position rule are the shared ones (`sortEntries`, `UNPOSITIONED`); a new certification gets `bottomPosition(list)` (exists in `src/lib/admin/list.ts`). `certifications` holds no other kind of document. The uploaded images are read from `images` through the existing `listImages()` and never written.

### 2.6 Non-functional notes

- Static export holds: no server, route or generated param is added; the editor is a client component reached only through `AdminPanel`, and Firestore is touched only inside effects and handlers.
- Public pages stay Firebase-free (E2E-17).
- Internal admin panel for one owner: no autosave, no draft, no conflict check, no field-length limit, no pagination; long text wraps.
- Tokens only for colour (the ones `formParts.tsx` already uses); no `<img>`, no `next/image`, no thumbnail (story Deferred).
- Accessibility: every control is a native input, select or button reached by keyboard; each error is linked to its field with `aria-describedby`.
- No `eslint-disable` or `@ts-ignore` line is added anywhere; the new component sets state only after an `await` in its image-loading effect (the Profile editor's shape), never synchronously.
- None of the new files holds the word `email` (`admin-sign-in` E2E-15 searches every admin source for it).
