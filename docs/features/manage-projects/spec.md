## 1. Business analysis — BA

### 1.1 Purpose

The owner wants to keep the project list current without opening the code. Choosing "Projects" in the admin menu shows the saved projects in saved order and lets the owner add a project, edit it, move it up or down one place, and delete it after confirming. A project has a title, a short description, a list of description paragraphs, a list of tech names, a GitHub link and a demo link; only the title is required. Nothing is prefilled from today's site, so the first time the list is empty. This screen reuses the list editor that `manage-experience` built: the list, the form shell with Save and Cancel, Move up and Move down, the in-row delete confirmation, the messages and the busy guard are shared, and this slice only says what a project's fields are. It does not change what visitors see (phase 2).

### 1.2 Actors & preconditions

- **Owner:** the single Google account whose user ID is in the rules and in the panel's owner constant. Saving, moving and deleting work only for them once the ID is filled in.
- **Unfilled owner:** signed in while the user ID is still the placeholder; the panel shows the saving-off notice, the list loads (`projects` is publicly readable) and every write is refused by the rules.
- **Other account / visitor:** never see the editor; `admin-sign-in` and `admin-owner-only-access` cover them, and the editor is rendered only on the allowed screen.
- Preconditions met by hand (intent §7): the owner's user ID in the rules and the panel constant. No automated row depends on them; every row runs against the local emulators.

### 1.4 Data touched

One collection of the database, `projects`: one document per project holding the title, short description, paragraphs, tech names, two links, the project's place in the list (`position`, a number) and the time of the last write. The editor reads the whole collection (publicly readable by the rules), adds a document, updates the content fields of one, updates only the place of the projects a move changes, and deletes one. It reads nothing from the signed-in account and uses no browser storage.

## 2. Technical specification — SA

### 2.1 Approach

The shared list editor from `manage-experience` does the work; this slice adds the three-file configuration that spec's D-21 names, plus the smallest extension the story needs. `src/lib/admin/projects.ts` is pure (types, texts, check, tolerant read, label). `src/lib/firebase/projects.ts` is one line binding `createListStore` to the `projects` collection. `ProjectsEditor.tsx` renders `ListEditor` with the Projects fields (Title, Short description, GitHub link, Demo link, and two add-and-remove line lists for paragraphs and tech names). Two story facts differ from Experience, so `ListEditor` gains three optional props whose defaults reproduce Experience exactly: `emptyText` (the story says "No projects yet"), `listLabel` (the story says "Projects list") and `newPosition` (the story puts a new project at the end, Experience puts it at the top); `list.ts` gains the pure `bottomPosition` for it. `AdminPanel` renders the editor for the "Projects" item on the allowed screen only. The rules need no change: `firestore.rules` already lets anyone read and only the owner write `projects/{id}`. Three earlier tests that used "Projects" as the example placeholder move to "Certifications". The rows are pure (`projects.ts`, `bottomPosition`) and screen rows for the seven scenarios, the new-at-the-end rule, link validation, the refusal wiring, the menu and the public pages; the shared behaviour already proved by `manage-experience` is re-run, not copied.

### 2.3 Data model

```ts
// src/lib/admin/list.ts (pure; one export added)
export function bottomPosition<T>(entries: readonly ListEntry<T>[]): number;

// src/lib/admin/projects.ts (pure: no firebase, no window)
export const PROJECTS_COLLECTION: string;                          // "projects"
export type ProjectContent = {
  title: string; shortDesc: string;
  description: string[];                                           // paragraphs, in order
  tech: string[];                                                  // tech names, in order
  github: string; demo: string;
};
```

Firestore: collection `projects`, one document per project, a new unique string id, fields exactly `title`, `shortDesc`, `github`, `demo` (strings), `description`, `tech` (arrays of strings), `position` (a number, integer valued) and `updatedAt` (`Date.now()` at the last write, milliseconds). Order, ties and the missing-position rule are the shared ones (`sortEntries`, `UNPOSITIONED`). A new project gets `bottomPosition(list)`: the largest position below `UNPOSITIONED` plus 1, or 0 when the list has none (`[]` gives 0, places `[0,1]` give 2, `[5,-3]` give 6, `[UNPOSITIONED]` gives 0, `[UNPOSITIONED,7]` gives 8). A move renumbers the displayed list 0 to n−1 and writes only the changed places (shared). `projects` holds no other kind of document.

### 2.6 Non-functional notes

- Static export holds: no server, route or generated param is added; the editor is a client component reached only through `AdminPanel`, and Firestore is touched only inside effects and handlers.
- Public pages stay Firebase-free (E2E-18).
- Internal admin panel for one owner: no autosave, no draft, no conflict check, no field-length limit, no pagination; long text wraps.
- Tokens only for colour (the ones `formParts.tsx` already uses); no `<img>`, no `next/image`.
- Accessibility: every control is a native input, textarea or button reached by keyboard; each error is linked to its field with `aria-describedby`; the confirmation is a labelled group.
- No `eslint-disable` or `@ts-ignore` line is added anywhere; the new component sets no state synchronously in an effect (it has no effect).
