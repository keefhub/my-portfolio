**Risks**

- R-1 (the `ListEditor` additions drift the three earlier screens): the new members are read in four places; a wrong default would change the delete text or the row on shipped screens. Likelihood low, cost medium. Carried: D-09, Step 2 Verify re-runs the three earlier specs (placeholder tests excluded until Step 3, D-25).
- R-2 (the image list cannot be read, so a stored uploaded address matches no image and the check refuses it): the owner sees the alert `The uploaded images could not be loaded.` and the address in the path field; a save is refused with `Icon path must start with "/"` until a reload brings the images back, or the owner types a path. Likelihood low for the owner (the same account that uploaded can read), cost low. Carried: D-14, BR-04d, E2E-17.
- R-3 (the `techCategories` collection can hold documents an earlier spec wrote): `e2e/admin-owner-only-access.spec.ts` seeds and probes `techCategories` documents (lines 140, 197-203). They may stay in the shared emulator. Carried: `ownerSession` clears `techCategories` and `images` first and `techFromData` reads any shape as text and an empty list, so they cannot reach a row (E2E-16 seeds hand-written shapes on purpose).
- R-4 (a stale tab saves a category over another tab's edit): last save wins, as for every list. Likelihood very low (one editor), cost low. Carried: D-04.
- R-5 (a confirmed item removal also saves the other values in the open form): `saveNow` writes the whole form, so a typed rename is saved with the removal. Likelihood medium, cost low (the owner sees Save-like behaviour: the form closes and `Entry saved` shows). Carried: D-11, BR-09b.

- `e2e/admin-owner-only-access.spec.ts` and `e2e/manage-image-library.spec.ts` name "Tech stack" only inside the menu arrays, so they need no edit.
