## 1. Business analysis — BA

### 1.1 Purpose

The owner wants to keep the tech stack list current without opening the code. Picking "Tech stack" in the admin menu shows the saved categories in saved order, each with the items in it, and lets the owner add a category, edit it, move it up or down one place, and delete it after confirming. A category has a name and an ordered list of items; an item has a name and an icon. All three are required. The icon is either an image picked from the owner's uploaded images (the image library) or a repo path typed as text such as `/icons/react.png`, one source at a time, the same pattern as the Profile photo and the Certification badge. Inside a category the owner adds items, edits them, moves them up or down, and deletes one after confirming; a confirmed item removal is saved at once. Nothing is prefilled from today's site, so the first time the list is empty. The screen reuses the list editor built by `manage-experience` (list, form shell with Save and Cancel, category Move up and Move down, in-row delete confirmation, messages, busy guard). The nested item rows are this slice's own part of the form.

### 1.2 Actors & preconditions

- **Owner:** the single Google account whose user ID is in the rules and in the panel's owner constant. Saving, moving and deleting work only for them once the ID is filled in.
- **Unfilled owner:** signed in while the user ID is still the placeholder; the panel shows the saving-off notice, the list loads (`techCategories` is publicly readable), the uploaded-image list does not (`images` is owner-only) and every write is refused by the rules.
- **Other account / visitor:** never see the editor; `admin-sign-in` and `admin-owner-only-access` cover them, and the editor is rendered only on the allowed screen (story Assumption 15).
- Preconditions met by hand (intent §7): the owner's user ID in the rules and the panel constant. No automated row depends on them; every row runs against the local emulators.

### 1.4 Data touched

Two collections of the database. `techCategories`: one document per category holding the category name (`category`), its items in order (`tools`, each with `name` and `icon`, the icon being an uploaded image's public address or a repo path in one text), the category's place in the list (`position`, a number) and the time of the last write. The editor reads the whole collection (publicly readable by the rules), adds a document, replaces the content fields of one, updates only the place of the two categories a move changes, and deletes one. `images`: read only, to list the uploaded images by name for the chooser (owner-only by the rules, written by the image library, never written here). It reads nothing from the signed-in account and uses no browser storage.

### 1.6 Out of scope

Uploading images from the editor; previewing an icon or checking that a typed path points to a file; changing what visitors see on the public Tech stack section; importing today's tech stack from the code; moving an item to another category (remove it and add it again); dragging to reorder; undoing or restoring a delete; a warning about unsaved changes or a second tab; a limit on categories or items; bulk edits, search or filtering; the non-owner and signed-out screens (`admin-sign-in`, `admin-owner-only-access`); the other list editors.

## 2. Technical specification — SA

### 2.1 Approach

The shared list editor does the category list; this slice adds the usual three-file configuration plus the little the nested items force. `src/lib/admin/techstack.ts` is pure: types, texts, the check (which takes the list of uploaded image addresses), the tolerant read, the item move, the row line and the delete wording. `src/lib/firebase/techstack.ts` is one line binding `createListStore` to `techCategories`. `TechStackEditor.tsx` loads the uploaded-image list once (the Certifications editor's pattern) and renders `ListEditor` with the category fields: a Category name and an Items group of nested item groups, each holding a name, an "Uploaded image" chooser, an icon path and the buttons "Move up", "Move down" and "Delete" with a confirmation that is local to the item. Item reordering happens in the form and is stored by "Save"; category reordering stays the list's own at-once "Move up" and "Move down". An item removal confirmed in an edit form must be stored at once, and only `ListEditor` writes, so `ListEditor` gains four additive optional members: `rowDetails` (the item lines under a category name), `deleteText` (the category confirmation with the item count), and `mode` and `saveNow` in the props it hands to `renderFields` (so the form can store itself through the one existing write path). With the new members absent the Experience, Projects and Certifications screens behave exactly as before; Step 2 re-runs their specs. `AdminPanel` renders the editor for the "Tech stack" menu item, which leaves "Blog posts" as the only placeholder, so five earlier placeholder tests are edited where they clicked "Tech stack".

### 2.3 Data model

```ts
// src/lib/admin/techstack.ts (pure: no firebase, no window)
export const TECH_COLLECTION: string;        // "techCategories"
export const TECH_NAME_MAX: number;          // 80
export type TechItem = { name: string; icon: string };
export type TechCategoryContent = { category: string; tools: TechItem[] };
// icon: an uploaded image's public address, or a repo path, or ""
```

Firestore: collection `techCategories`, one document per category, a new unique string id, fields exactly `category` (string), `tools` (an array of maps, each exactly `name` and `icon`, both strings; the array may be empty), `position` (a number, integer valued) and `updatedAt` (`Date.now()` at the last write, milliseconds). The names are the public component's own (`src/app/components/techstack.tsx:5-13`: `category`, `tools[] { name, icon }`), so phase 2 reads the same fields. Order, ties and the missing-position rule are the shared ones (`sortEntries`, `UNPOSITIONED`); a new category gets `bottomPosition(list)` (exists in `src/lib/admin/list.ts`). `techCategories` holds no other kind of document. The uploaded images are read from `images` through the existing `listImages()` and never written. A save writes the whole `tools` array, so a removed item leaves no trace.

### 2.6 Non-functional notes

- Static export holds: no server, route or generated param is added; the editor is a client component reached only through `AdminPanel`, and Firestore is touched only inside effects and handlers.
- Public pages stay Firebase-free (E2E-20).
- Internal admin panel for one owner: no autosave, no draft, no conflict check, no pagination; names are limited to 80 characters (story Assumption 6); long text wraps.
- Tokens only for colour (the ones `formParts.tsx` already uses); no `<img>`, no `next/image`, no thumbnail (an icon is shown as text).
- Accessibility: every control is a native input, select or button reached by keyboard; each error is linked to its field with `aria-describedby`; each item is a labelled group.
- No `eslint-disable` or `@ts-ignore` line is added anywhere; the new component sets state only after an `await` in its image-loading effect (the Certifications editor's shape), never synchronously, and holds no hook inside the `renderFields` function.
- None of the new files holds the word `email` (`admin-sign-in` E2E-15 searches every admin source for it).
