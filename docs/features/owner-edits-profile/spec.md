## 1. Business analysis — BA

### 1.1 Purpose

The owner edits the one profile record (name, headline, about paragraphs, photo path, email, resume link, social links) in the panel's Profile screen, saves it, and finds it again after a reload. It is the first feature that uses the database: the profile is kept in Supabase PostgreSQL, read and written only by the server, and only for the owner. When the database cannot be reached the Profile screen says so and nothing else in the panel or on the public site is affected. Saving the profile does not change the public site (public pages keep showing the repository's content).

### 1.2 Actors & preconditions

- **The owner**: signed in with the Google account whose verified email equals `ADMIN_EMAIL` (built by `owner-google-sign-in`, commit 61abc37). Sees the seven-item menu.
- **A signed-out visitor** and **a signed-in account that is not the owner**: must be refused on every request, including a request sent without the panel.
- **The database**: Supabase PostgreSQL, empty at first, nothing imported from the earlier panel (story Assumption 9).
- The "Profile" menu item and the "Sign out" control already exist; the notice "Profile editor is not available yet." is replaced for Profile only (Assumption 1).

## 2. Technical specification — SA

### 2.1 Approach

The server gets one owner-only route handler, `GET` and `PUT` at `/api/admin/profile/`, which asks `getPanelState()` (the earlier feature's single owner decision) before it touches anything, validates and normalises every save with the earlier panel's `checkProfile`, and answers with fixed JSON and fixed status codes. The data layer is three small server-only modules: the SQL text (one table, one row), the database module (the `postgres` client with the Supabase pooler's settings, the schema applied once per process, every failure turned into one fixed error and one fixed log line) and the profile store. For automated tests the database module honours a stand-in: when the setting starts with `stand-in:`, the rest is a JSON file path that the test run creates, seeds and breaks. The Profile screen is a client component that fetches the route, shows the earlier panel's form and messages, and the panel shell shows it in place of the "not available yet" notice. The SQL was proven on PostgreSQL by a throwaway script (impact.md SF-2, SF-6); nothing in the suite runs it, so the owner's SIT check is the only test of the real database (decomposition Open finding 1).

### 2.3 Data model

```ts
// src/lib/admin/profile.ts (existing, unchanged)
type SocialLink = { label: string; url: string };
type ProfileContent = {
  name: string; headline: string; about: string[]; photo: string;
  email: string; resumeLink: string; socialLinks: SocialLink[];
};
```

**Table** (created by the app; the exact text is in Step 2):

| Column | Type | Meaning |
| ------ | ---- | ------- |
| `id` | `text primary key` | always `"main"` (`PROFILE_DOC_ID`) |
| `data` | `jsonb not null` | the whole `ProfileContent` as normalised by `checkProfile` |
| `updated_at` | `timestamptz not null default now()` | set on every write |

**Route** `/api/admin/profile/` (JSON, every response has `Cache-Control: no-store`):

| Method | Requester | Status | Body |
| ------ | --------- | ------ | ---- |
| GET | owner, a profile stored | 200 | `{ "profile": ProfileContent }` (`profileFromData` of the stored value) |
| GET | owner, nothing stored | 200 | `{ "profile": null }` |
| PUT | owner, valid body | 200 | `{ "profile": ProfileContent }` (the normalised content that was stored) |
| PUT | owner, invalid or wrongly shaped or unparsable body | 400 | `{ "error": "invalid" }` |
| GET, PUT | signed out | 401 | `{ "error": "not-signed-in" }` |
| GET, PUT | signed in, not the owner (other account, or the owner's address with an unverified email) | 403 | `{ "error": "not-allowed" }` |
| GET, PUT | owner, any database or unexpected failure | 503 | `{ "error": "unavailable" }` |

**Stand-in file** (path = the part of `SUPABASE_DB_URL` after `stand-in:`): absent → a reachable, empty database. Present → a JSON object `{ "profile"?: <the stored value>, "unreachable"?: true }`. `unreachable: true`, an unreadable file or a file that is not a JSON object → every read and write fails. A write replaces `profile` and keeps nothing else.

**Log line**: `[database] <schema|read|write> failed <code>`, where `<code>` is the error's string `code` when it matches `^[A-Za-z0-9_]{1,20}$`, else `unknown`.

### 2.6 Non-functional notes

- **Size**: one owner, one record, a few saves a month; one connection per server instance (`max: 1`), no caching, no retry loop.
- **Time limits**: the client gives up on a request after 15 seconds; the server gives up on connecting after 5 seconds and on a query after 8 seconds (`postgres` options), so a hung pooler ends in the failure message.
- **Accessibility**: every field has a visible label; errors are `role="alert"` and linked to their field with `aria-describedby`; "Saving…", "Profile saved", "No profile has been saved yet." and "Loading profile…" are `role="status"`.
- **Theme and layout**: inline styles from the shared `formParts` token styles only; values wrap (`overflowWrap: "anywhere"`); no raw colours.
- **Privacy**: no message, response or log carries an address, password, key or database error text (BR-19); the log line carries an allow-listed code.
- **Cost**: Supabase free plan; nothing here needs a paid feature.

### 2.7 Decisions made (do not revisit)

- **D-1 [human: intent §4]** A PostgreSQL client library is approved. **[auto]** The choice is `postgres` at the exact version `4.1.1`: it ships its own types (no second package), its documentation covers Supabase's pooler (`prepare: false`, `max_pipeline: 1`, `query_timeout`), and it bundles under this repo's Next with no configuration (impact.md SF-5). `3.4.7` is the fallback if the SIT check fails on the pooler (R-2, R-5).
- **D-2 [human: intent §4]** Supabase PostgreSQL holds the profile. **[auto]** One table `profile` with the columns of § 2.3 and one row `id = "main"`; the whole record is one `jsonb` value. Why: the smallest possible SQL (one read, one upsert) because no test database exists (decomposition Open finding 1), and `profileFromData` already tolerates any stored shape (Assumption 14). The decomposition's "same fields" is met: the fields are the same, inside `data`.
- **D-3 [human: intent §4]** One new setting name, **`SUPABASE_DB_URL`** **[auto: the name]**: the connection string of Supabase's transaction pooler, password included. The owner sets it in Vercel for Production and for SIT. It is listed for the pull request. No storage or other setting is added here (`owner-uploads-images` adds its own).
- **D-4 [auto]** (decomposition Decision 11) The schema is applied by the app, once per server process, before the first read or write, by running `SCHEMA_STATEMENTS` in order; a failure is not remembered, so the next request tries again. The decomposition said "one SQL file"; it is one TypeScript module (`src/lib/server/sql.ts`) because a `.sql` file would need file tracing on Vercel.
- **D-5 [auto]** Row level security is switched on for the table in the schema statements, with no policy. Why: Supabase publishes tables of the `public` schema through its Data API to anyone holding the project's public key (documented behaviour, not checked here); with no policy that API sees nothing, while the app's own connection (the table owner) should be unaffected. Whether the pooler's role bypasses it is unproven (SF-6, E2E-30).
- **D-6 [auto]** (decomposition Decision 8) The entry point is a route handler at `/api/admin/profile/`, `GET` and `PUT`, not a Server Action, so that "a request sent without the panel" can be tested. The client calls the slashed address; the unslashed one answers 308 (SF-4). Statuses and bodies are those of § 2.3.
- **D-7 [auto]** (decomposition Decision 7, Open finding 1) The database stand-in lives in the repo (`src/lib/server/standin.ts`), is chosen by a value that starts with `stand-in:`, and needs no new setting name: the test run's `SUPABASE_DB_URL` is `stand-in:` followed by a temp file path. The tests seed, break and read that file directly. Rejected: a fake PostgreSQL wire-protocol server (needs a SQL parser), a test-only HTTP route (production surface), `@electric-sql/pglite` (present only through `firebase-tools`, which `retire-firebase` removes, and not approved). Cost: the suite never runs the SQL (R-2).
- **D-8 [auto]** Refusals: `401 {"error":"not-signed-in"}` for no valid session, `403 {"error":"not-allowed"}` for a valid session that is not the owner; any database or unexpected failure is `503 {"error":"unavailable"}`; an invalid body is `400 {"error":"invalid"}`. The owner check runs before the body is read and before any database call, so a refusal never depends on the database.
- **D-9 [auto]** Client: `fetch` with `cache: "no-store"` and `AbortSignal.timeout(15000)`; a non-ok status, a network error, a timeout or an unreadable body is one failure (the load message, or the save message). Server: the exact `postgres` options are `max: 1`, `connect_timeout: 5`, `query_timeout: 8`, `idle_timeout: 20`, `prepare: false`, `max_pipeline: 1`, `ssl: "require"`, `onnotice: false`.
- **D-10 [auto]** `ssl: "require"` encrypts but does not verify Supabase's certificate (verifying needs a CA file in the repo). Accepted for a one-owner site (R-3).
- **D-11 [auto]** One message line sits above the form: "Saving…", then "Profile saved" or the failure alert. It stays until the next "Save" or until the screen is left; typing does not clear it. "No profile has been saved yet." is a second line that stays until the first successful save. The loading text "Loading profile…" keeps the earlier wording and is not asserted by a test.
- **D-12 [auto]** The log line is `[database] <schema|read|write> failed <code>` (§ 2.3). The code helps the owner diagnose SIT (for example `ECONNREFUSED`, `28P01`) and is not text of the database's message. The line is computed into a variable and then logged, so the gate's LOG-ERROR check does not fire.
- **D-13 [auto]** An unset or blank `SUPABASE_DB_URL` is an unreachable database: the same fixed error, logged with code `unknown`. There is no start-up check.
