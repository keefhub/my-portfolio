## 1. Business analysis — BA

### 1.1 Purpose

The owner opens the private panel at `/bright-warm-greenhouse/`, signs in with their own Google account and sees a menu of seven screens. Any other Google account, including the owner's address when Google has not verified it, is told it is not allowed and sees nothing. The owner can sign out and sign in again, and a sign-in that is not completed shows a message and leaves the button usable. The public site is unchanged and ships no sign-in code. To make this possible the static export is lifted for sign-in and the panel only (intent §2.4, §4); this feature also amends the standing docs that lift makes false.

### 1.2 Actors & preconditions

- **Owner:** the one person whose verified Google email equals the `ADMIN_EMAIL` setting. Only user of the panel (intent §2.3).
- **Other Google account:** any account that signs in but is not the owner.
- **Visitor:** anyone not signed in; reads public pages only; the site stores nothing about them.
- **Preconditions:** Vercel hosts the site; the owner has created the Google sign-in app and set `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` and `ADMIN_EMAIL` in Vercel for Production and SIT (intent §7, human-only). The agent never sees a value.

### 1.4 Data touched

- The owner's verified Google email, read from the sign-in session only to decide the screen. It is never shown, stored by the site, or sent to the browser by the page.
- A sign-in session held in a cookie in the visitor's own browser, created only when someone signs in. No database, no file store (Assumption 14).
- Four settings read by name at run time: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, `ADMIN_EMAIL`. Values live only in Vercel.

### 1.5 Edge cases & negative paths

- Owner email has different case or surrounding spaces in the setting [in spec] (Assumption 2).
- Setting missing, empty or only spaces [in spec] (Assumption 4). An empty email never equals an empty setting [derived].
- An email that merely starts or ends like the setting (`xowner@…`, `owner@….evil.test`) is not the owner [derived].
- The owner's email not verified by Google [in spec] (Scenario 3).
- A signed-in non-owner reloads, or opens a second tab [in spec] (Assumption 5).
- Setting changed while someone is signed in: the old account is refused on its next reload [in spec] (Assumption 3); expressed as "the check runs per request, uncached".
- Cookie is random text, expired, or minted with another secret [in spec] (Assumption 7).
- Double click on "Sign in with Google" [in spec] (Assumption 10).
- Google returns an error; return address requested with and without a trailing slash [in spec; the slash form is [derived] from `trailingSlash: true`].
- The panel response being cached by a shared cache [derived].
- A public page that silently becomes dynamic because it reads the session [derived] (intent §8 pitfall).
- An unknown blog address being rendered on demand and failing instead of showing the 404 page [derived].
- Leftover old admin specs that cannot pass once the panel stops rendering the Firebase editors [derived]; handled in Decision D13 and Section 7.
- The mechanical gate failing this feature's own Server Action file, auth handler or `next-auth` import because its rules were written for the static export [derived]; handled by Decision D22 and Step 2.

## 2. Technical specification — SA

### 2.1 Approach

`next.config.ts` and `vercel.json` stop exporting a static site, so the panel page and `/api/auth/*` run on Vercel's server while every public route stays prerendered (proved on a scratch copy, impact.md SF-1). Auth.js v5 (`next-auth`, exact pin) signs the owner in with Google by redirect and keeps the session in a signed, encrypted cookie; there is no database. A server-only module (`src/lib/auth.ts`) holds the Auth.js configuration and `getPanelState()`, which reads the session on every request and returns `signed-out`, `owner` or `not-allowed` using a pure function (`accessFor`) over the verified email and the `ADMIN_EMAIL` setting. The panel page is a dynamic server component that passes only that state and a failed-sign-in flag to the client `AdminPanel`, which renders the three screens and posts to Server Actions for sign-in and sign-out, so no Auth.js code ships to the browser and no client call to `/api/auth/*` is needed. Tests run against `next start` with a per-run `AUTH_SECRET`, mint session cookies with it, and stand in for Google at the browser boundary; the real Google token exchange is checked once by the owner on SIT. The mechanical gate's STATIC and IMPORTS checks were written for the static export and would fail the Server Action file, the auth handler and the `next-auth` import, so one earlier Step makes the smallest allowance for exactly those (D22).

### 2.3 Data model

No persisted store. The session is a JWT in a cookie (`authjs.session-token` over http, `__Secure-authjs.session-token` over https), whose claims this feature relies on:

```ts
type SessionClaims = {
  sub: string;
  email?: string | null;
  name?: string | null;
  emailVerified: boolean; // set from Google's email_verified claim on first sign-in
};
export type PanelState = "signed-out" | "owner" | "not-allowed";
```

The cookie also carries the library's default claims (`picture`, `iat`, `exp`, `jti`). The page passes only `{ state, failed }` to the client, so none of these reaches the browser as page content.

Settings read by name (values only in Vercel): `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` (read by Auth.js), `ADMIN_EMAIL` (read in `getPanelState`, per request).

### 2.7 Decisions made (do not revisit)

- **D1 [human: intent §4]** `next-auth` v5 is added at one exact version, no range. The version is `5.0.0-beta.32`, the registry's `beta` tag on 2026-11-27, whose peer range includes `next ^16.0.0` [auto: version choice].
- **D2 [human: intent §4]** The only new settings are `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, `ADMIN_EMAIL`. Names only in the repo. `AUTH_URL`, `AUTH_TRUST_HOST`, `AUTH_GOOGLE_ISSUER` and every other Auth.js setting are not used; `trustHost: true` is set in code [auto] because under `next start` neither `VERCEL` nor `AUTH_URL` exists.
- **D3 [human: intent §4]** Google sign-in app (owner-created) with return addresses `https://thegoldenpothos.xyz/api/auth/callback/google`, `https://sit.thegoldenpothos.xyz/api/auth/callback/google`, `http://localhost:3000/api/auth/callback/google`; Vercel hosting; the static-export lift applies to sign-in and the panel only. The pull request lists the four setting names and the three return addresses.
- **D4 [human: intent §4]** The owner is recognised by the verified Google email in `ADMIN_EMAIL`, compared per `accessFor`: both values trimmed and lower-cased; Google's `email_verified` must be exactly `true`; a blank setting matches nobody.
- **D5 [auto]** Auth.js uses the redirect flow with a JWT session in a cookie, no adapter, no database. Cookie names are Auth.js defaults (`authjs.session-token`, `__Secure-` prefix over https). Session length is the Library default (story Deferred).
- **D6 [auto]** Sign-in and sign-out are Server Actions in `src/app/bright-warm-greenhouse/actions.ts` posted from `<form action>`, not `next-auth/react`. Why: no Auth.js code reaches any browser bundle, and the browser never calls `/api/auth/*` itself; the only request to it is Google's return redirect. The earlier decomposition Decision 8 (route handlers for the data entry points) is unaffected: it applies to later content slices.
- **D7 [auto]** Every Google account may sign in; the page, not a `signIn` callback, decides the screen on each request, because the story keeps a non-owner signed in on a "not allowed" screen (Assumption 5).
- **D8 [auto]** The page passes `AdminPanel` exactly `{ state: PanelState, failed: boolean }`. `failed` is true only when `state` is `signed-out` and the `error` query is present (any value, even empty). Auth.js `pages.signIn` and `pages.error` are both `/bright-warm-greenhouse/`, so every Auth.js error lands on the panel with `?error=<type>`.
- **D9 [auto]** "Checking sign-in…" is dropped. The state is known on the server before any markup is sent, so neither the sign-in control nor the menu can show before it is known, which was the purpose of that text (Assumption 6).
- **D10 [auto]** `src/lib/admin/owner.ts` (user-ID based, imports Firebase config) is deleted and replaced by the new module `src/lib/admin/access.ts`; no `OWNER_UID` or `SIT_OWNER_UID` remains.
- **D11 [auto]** Tests stand in for Google at the browser boundary only: a context route on `https://accounts.google.com/**` either "approves" (adds a minted session cookie and redirects to the panel) or "leaves" (redirects to `/api/auth/callback/google?error=access_denied&iss=https%3A%2F%2Faccounts.google.com`). Session cookies are minted with `encode` from `next-auth/jwt` using the run's `AUTH_SECRET`. No new setting, no new package. Google's token exchange and ID-token check are not exercised by automation; the owner's SIT check covers them (E2E-32).
- **D12 [auto]** `playwright.config.ts` serves with `npx next start -p 3100`, `baseURL` is `http://localhost:3100` (not `127.0.0.1`: under `next start` the request URL host is always `localhost`, so a `127.0.0.1` page would be sent back to a different origin), `reuseExistingServer` is `false` (a reused server holds another secret), and the four settings get fresh random values per run (`ADMIN_EMAIL` is `owner-<hex>@example.test`) assigned only when `TEST_WORKER_INDEX` is undefined, so workers inherit the main process's values. The Firebase emulator server entry is removed now (intent §8: no emulator, no Java), which the earlier decomposition left to retire-firebase.
- **D13 [auto]** `e2e/admin-sign-in.spec.ts` and `e2e/admin-owner-only-access.spec.ts` are deleted here: this feature replaces both stories.
