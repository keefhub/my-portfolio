## 1. Business analysis — BA

### 1.1 Purpose

The owner adds, edits, reorders and deletes certifications in the panel's Certifications screen, and they are kept in Supabase PostgreSQL, read and written only by the server and only for the owner. Each certification has a name, a badge image and a credential link. The badge image is either an image the owner uploaded in "Images" or a path to a file in the site's public files. This replaces the "Certifications editor is not available yet." notice. It reuses the shared list pattern that `owner-manages-experience` built and `owner-manages-projects` reused (the list screen, the browser list store, the owner-only list route, the generic list service and list SQL), adding only what is particular to a certification: its fields and rules, a table name, a route file, and an editor that puts a new certification at the bottom of the list and offers the image picker that `owner-uploads-images` built for the profile photo. The public Certifications section keeps showing the certifications that are in the repository.

### 1.2 Actors & preconditions

- **The owner**: signed in with the Google account whose verified email equals `ADMIN_EMAIL` (built by `owner-google-sign-in`). Sees the seven-item menu; Profile, Images, Experience and Projects already open screens.
- **A signed-out visitor** and **a signed-in account that is not the owner**: refused on every request to the new route, including one sent without the panel. A signed-out visitor can open an uploaded image at its public address (intent §5; OVERVIEW §2 item 7), which is what a certification stores when the owner picks an uploaded image.
- **The database**: Supabase PostgreSQL (`SUPABASE_DB_URL`, built by `owner-edits-profile`), empty at first; nothing is imported (story Out of Scope).
- **The image list**: the owner-only list of uploaded images (`/api/admin/images/`, built by `owner-uploads-images`), read by the browser beside the certifications.

- **The database setting** (`SUPABASE_DB_URL`): read on the server only; nothing new.

## 2. Technical specification — SA

### 2.1 Approach

This feature follows the reuse recipe of the experience spec (§ 2.4), as the projects spec did: a table name, a route file, an editor store, and the deletion of the collection's Firebase store and spec. `src/lib/server/listSql.ts` gains the name `certifications` in its closed set of table names, so the existing schema step also creates the table and the five existing database functions and the stand-in (already generic over the table name) serve it unchanged. A new owner-only route, `/api/admin/certifications/`, answers `GET`, `POST`, `PUT ?id=`, `PATCH` and `DELETE ?id=` through the existing `createListService`, given the certification's own `shape`, `check`, `fromData` and `toData`; `certificationShape` is the one new function in `src/lib/admin/certifications.ts`. In the browser `CertificationsEditor` swaps its Firestore store for `createHttpListStore("/api/admin/certifications/", certificationFromData, certificationToData)`, takes no props, keeps the earlier panel's fields, wording and messages, and still passes `bottomPosition` so a new certification goes to the bottom. It keeps the image picker it already has (`listImages`, `photoSelection`, `UploadedImage`), which loads the uploaded images beside the list and degrades to a typed path when they cannot be loaded, and it adds two text lines to each row (the badge image and the credential link) so that the story's "the list should show … with its badge image" can be seen without a thumbnail. `AdminPanel` shows it when Certifications is chosen. The earlier Firebase certifications store and spec are deleted, one line of the sign-in spec's notice loop and two places in the projects spec are amended (the exact table set it pins, and its list of Firebase files that must exist), and `CLAUDE.md` names the route. The SQL for `certifications` was run on PostgreSQL by a throwaway script (impact.md SF-2); nothing in the suite runs it, so the owner's SIT check is the only test of the real database.

### 2.3 Data model

```ts
// src/lib/admin/certifications.ts (existing; one export added)
type CertificationContent = { name: string; icon: string; url: string };
// icon is the badge: an uploaded image's public address, or a repo path, or an http(s) address as text
// new: certificationShape(input: unknown): CertificationContent | null

// src/lib/server/listSql.ts (existing; the set grows by one name)
type ListTable = "experience" | "projects" | "certifications";
const LIST_TABLES: readonly ListTable[]; // ["experience", "projects", "certifications"]
```

**Table** `certifications` (created by the app, the same text as `experience` with the name changed):

| Column | Type | Meaning |
| ------ | ---- | ------- |
| `seq` | `bigint generated always as identity` | insertion order, breaks ties in `position` |
| `id` | `text primary key` | a version 4 UUID made by the server (`crypto.randomUUID()`) |
| `position` | `integer not null` | list order, lowest first; the screen sends the bottom position for a new certification |
| `data` | `jsonb not null` | the three fields as `certificationToData` writes them (`name`, `icon`, `url`), normalised by `checkCertification` |
| `updated_at` | `timestamptz not null default now()` | set on every write |

**Route** `/api/admin/certifications/` (JSON; every response has `Cache-Control: no-store`):

| Method and query | Requester | Status | Body |
| ---------------- | --------- | ------ | ---- |
| `GET` | owner | 200 | `{ "entries": [ { "id": string, "position": number, "content": CertificationContent } ] }` ordered by `position` then insertion; `{ "entries": [] }` when empty; `content` is `certificationFromData` of the stored value |
| `POST`, body `{ "content": CertificationContent, "position": integer }` | owner | 200 | `{ "id": string }` |
| `PUT ?id=<id>`, body `{ "content": CertificationContent }` | owner | 200 | `{ "updated": true }` |
| `PATCH`, body `{ "changes": [ { "id": string, "position": integer } ] }` | owner | 200 | `{ "moved": true }` |
| `DELETE ?id=<id>` | owner | 200 | `{ "deleted": true }` |
| `PUT`, `PATCH`, `DELETE` naming an id with no stored certification | owner | 404 | `{ "error": "not-found" }`; nothing is stored |
| any, invalid body, id, position or changes | owner | 400 | `{ "error": "invalid" }`; nothing is stored |
| any | signed out | 401 | `{ "error": "not-signed-in" }` |
| any | signed in, not the owner (other account, or the owner's address with an unverified email) | 403 | `{ "error": "not-allowed" }` |
| any | owner, any database or unexpected failure | 503 | `{ "error": "unavailable" }` |

A position is a safe integer from -2147483648 to 2147483647. An id is a string matching `LIST_ID_PATTERN` (the shared pattern of `src/lib/admin/list.ts`).

**Stand-in file** (path = the part of `SUPABASE_DB_URL` after `stand-in:`): the key `certifications` holds an array of `{ "id": string, "position": number, "data": <stored value> }` in insertion order; absent or not an array → empty. Writing `certifications` keeps every other key (`profile`, `images`, `experience`, `projects`, `unreachable`). The existing rules for `unreachable: true`, an unreadable file or a file that is not a JSON object stay.

- **Size**: one owner, a handful of certifications; the whole list is loaded at once; no paging, no cap.

- **Privacy**: no message, response or log carries an address, password, key or database error text (the `run` wrapper's rule, unchanged). An uploaded image's public address holds no token or key.
- **Cost**: Supabase free plan; one more small table; no new storage call (the picker reads the list the Images screen already uses).
