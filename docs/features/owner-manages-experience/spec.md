## 1. Business analysis — BA

### 1.1 Purpose

The owner adds, edits, reorders and deletes work-history entries in the panel's Experience screen, and they are kept in Supabase PostgreSQL, read and written only by the server and only for the owner. It replaces the "Experience editor is not available yet." notice. It is also the first list screen, so it fixes the pattern the Projects, Certifications and Tech stack slices reuse: the list screen (Add, Edit, Move up and Move down, confirm before Delete, the busy guard and the messages), a browser list store over the server, an owner-only list route, and one generic list service and list SQL for a table. The public landing page keeps showing the experience that is in the repository.

### 1.2 Actors & preconditions

- **The owner**: signed in with the Google account whose verified email equals `ADMIN_EMAIL` (built by `owner-google-sign-in`, 61abc37). Sees the seven-item menu; Profile and Images already open screens.
- **A signed-out visitor** and **a signed-in account that is not the owner**: refused on every request to the new route, including one sent without the panel.
- **The database**: Supabase PostgreSQL (`SUPABASE_DB_URL`, built by `owner-edits-profile`, 9c66c1a), empty at first; nothing is imported (story Assumption 10).

## 2. Technical specification — SA

### 2.1 Approach

The profile slice's route pattern and the images slice's second table are reused. One owner-only route, `/api/admin/experience/`, answers `GET` (list), `POST` (add), `PUT ?id=` (replace one), `PATCH` (reorder) and `DELETE ?id=` (remove), asking `getPanelState()` before it reads a body or calls the database. Its logic lives in a generic server list service (`src/lib/server/listStore.ts`) that validates ids, positions and the body shape, applies the record's own `check` function, and calls five new generic database functions for a table from a closed set (`experience` now; each later list slice adds its own name and no new mechanism). The SQL is one table `experience (seq, id, position, data jsonb, updated_at)`, created by the app on first use like the other tables. The reorder is one all-or-nothing statement. In the browser a small list store (`createHttpListStore`) implements the existing `ListStore<T>` contract over `fetch`, so the shared `ListEditor` and the earlier panel's fields, wording and messages stay as they are; only the store behind `ExperienceEditor` changes from Firestore to the route. The `ListStore<T>` type moves into `src/lib/admin/list.ts` so the shared screen no longer imports a Firebase file. The SQL was run on PostgreSQL by a throwaway script (impact.md SF-2); nothing in the suite runs it, so the owner's SIT check is the only test of the real database.

### 2.3 Data model

```ts
// src/lib/admin/experience.ts (existing; one export added)
type ExperienceContent = {
  year: string; title: string; company: string;
  duration: string; description: string; details: string[];
};
// new: experienceShape(input: unknown): ExperienceContent | null

// src/lib/admin/list.ts (existing; one type and one pattern added)
type ListStore<T> = {
  load(): Promise<ListEntry<T>[]>;
  add(content: T, position: number): Promise<string>;
  update(id: string, content: T): Promise<void>;
  reorder(changes: { id: string; position: number }[]): Promise<void>;
  remove(id: string): Promise<void>;
};
const LIST_ID_PATTERN: RegExp; // /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/
```

**Table** (created by the app; exact text in Step 2):

| Column | Type | Meaning |
| ------ | ---- | ------- |
| `seq` | `bigint generated always as identity` | insertion order, breaks ties in `position` |
| `id` | `text primary key` | a version 4 UUID made by the server (`crypto.randomUUID()`) |
| `position` | `integer not null` | list order, lowest first; new entries get the client's top position |
| `data` | `jsonb not null` | the six fields as `experienceToData` writes them, normalised by `checkExperience` |
| `updated_at` | `timestamptz not null default now()` | set on every write |

**Route** `/api/admin/experience/` (JSON; every response has `Cache-Control: no-store`):

| Method and query | Requester | Status | Body |
| ---------------- | --------- | ------ | ---- |
| `GET` | owner | 200 | `{ "entries": [ { "id": string, "position": number, "content": ExperienceContent } ] }` ordered by `position` then insertion; `{ "entries": [] }` when empty; `content` is `experienceFromData` of the stored value |
| `POST`, body `{ "content": ExperienceContent, "position": integer }` | owner | 200 | `{ "id": string }` |
| `PUT ?id=<id>`, body `{ "content": ExperienceContent }` | owner | 200 | `{ "updated": true }` |
| `PATCH`, body `{ "changes": [ { "id": string, "position": integer } ] }` | owner | 200 | `{ "moved": true }` |
| `DELETE ?id=<id>` | owner | 200 | `{ "deleted": true }` |
| `PUT`, `PATCH`, `DELETE` naming an id with no stored entry | owner | 404 | `{ "error": "not-found" }`; nothing is stored |
| any, invalid body, id, position or changes (see Step 2) | owner | 400 | `{ "error": "invalid" }`; nothing is stored |
| any | signed out | 401 | `{ "error": "not-signed-in" }` |
| any | signed in, not the owner (other account, or the owner's address with an unverified email) | 403 | `{ "error": "not-allowed" }` |
| any | owner, any database or unexpected failure | 503 | `{ "error": "unavailable" }` |

A position is a safe integer from -2147483648 to 2147483647. An id is a string matching `LIST_ID_PATTERN`.

**Stand-in file** (path = the part of `SUPABASE_DB_URL` after `stand-in:`): the key `experience` holds an array of `{ "id": string, "position": number, "data": <stored value> }` in insertion order; absent or not an array → empty. Writing `experience` keeps every other key (`profile`, `images`, `unreachable`). The existing rules for `unreachable: true`, an unreadable file or a file that is not a JSON object stay.

### 2.6 Non-functional notes

- **Size**: one owner, a handful of entries; the whole list is loaded at once; no paging, no cap (Assumption 16). One connection per server instance, as today.
- **Time limits**: the browser gives up on a request after 15 seconds; the server's connect and query limits are the profile slice's.
- **Accessibility**: labels, `role="alert"` errors linked to their field with `aria-describedby`, and `role="status"` messages come from the existing `ListEditor`, `ExperienceEditor` and `formParts.tsx`; they are kept.
- **Theme and layout**: inline styles from the shared `formParts` token styles and the tokens `--surface-alt`, `--foreground`, `--muted`, `--accent-rose`, `--border`; no raw colour; values wrap (`overflowWrap: "anywhere"`).
- **Privacy**: no message, response or log carries an address, password, key or database error text (the `run` wrapper's rule, unchanged).
- **Cost**: Supabase free plan; one more small table.

### 2.7 Decisions made (do not revisit)

- **D-1 [human: intent §4]** The database is Supabase PostgreSQL through the built `postgres` library; no new dependency or setting name. **[auto]** No setting is added: the table is created on first use by the existing schema promise (decomposition Decision 11).
- **D-2 [auto]** (decomposition Decision 8) One route handler at `/api/admin/experience/` with five methods, not a Server Action and not one route per action, called at its slashed address. Ids travel in the query (`?id=`) as the images route does; bodies are JSON.
- **D-3 [auto]** Table `experience` with columns `seq`, `id`, `position`, `data jsonb`, `updated_at` (§ 2.3), read `order by position, seq`. Why: the smallest SQL, the same "whole record in `data`" choice as the profile (its D-2), and the decomposition's "position on list tables, `updated_at` on every row". `seq` makes ties deterministic (older first).
- **D-4 [auto]** The list service and list SQL are generic over a closed set of table names, and the route file is explicit (its `refusal()` and `reply()` helpers are copied, as the images route copied the profile's). Why: the next three slices reuse the service and SQL; a route factory would have to import `@/lib/auth` from outside the three prefixes the earlier feature's importer test allows (`src/app/api/auth/`, `src/app/api/admin/`, `src/app/bright-warm-greenhouse/`), and a few repeated lines are cheaper than a new rule.
- **D-5 [auto]** The id of a new entry is made by the server (`crypto.randomUUID()`), the position of a new entry is the client's (`topPosition` of the list it shows) and is stored as sent. Why: the Firestore store did the same, the screen's local list then always agrees with the stored positions in one tab, and the SQL stays a plain insert. A direct request may therefore place an entry anywhere; only the owner can send one.
