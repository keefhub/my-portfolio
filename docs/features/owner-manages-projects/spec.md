## 1. Business analysis — BA

### 1.1 Purpose

The owner adds, edits, reorders and deletes projects in the panel's Projects screen, and they are kept in Supabase PostgreSQL, read and written only by the server and only for the owner. It replaces the "Projects editor is not available yet." notice. It reuses the shared list pattern that `owner-manages-experience` built (the list screen, the browser list store, the owner-only list route, the generic list service and list SQL), adding only what is particular to a project: its fields and rules, a table name, a route file, and an editor that puts a new project at the bottom of the list. The public Projects section keeps showing the projects that are in the repository.

### 1.2 Actors & preconditions

- **The owner**: signed in with the Google account whose verified email equals `ADMIN_EMAIL` (built by `owner-google-sign-in`). Sees the seven-item menu; Profile, Images and Experience already open screens.
- **A signed-out visitor** and **a signed-in account that is not the owner**: refused on every request to the new route, including one sent without the panel.
- **The database**: Supabase PostgreSQL (`SUPABASE_DB_URL`, built by `owner-edits-profile`), empty at first; nothing is imported (story Out of Scope).

## 2. Technical specification — SA

### 2.1 Approach

This feature follows the reuse recipe of the experience spec (§ 2.4) exactly: a table name, a route file, an editor store, and the deletion of the collection's Firebase store and spec. `src/lib/server/listSql.ts` gains the name `projects` in its closed set of table names, so the existing schema step also creates the table and the five existing database functions and the stand-in (already generic over the table name) serve it unchanged. A new owner-only route, `/api/admin/projects/`, answers `GET`, `POST`, `PUT ?id=`, `PATCH` and `DELETE ?id=` through the existing `createListService`, given the project's own `shape`, `check`, `fromData` and `toData`; `projectShape` is the one new function in `src/lib/admin/projects.ts`. In the browser `ProjectsEditor` swaps its Firestore store for `createHttpListStore("/api/admin/projects/", projectFromData, projectToData)`, takes no props, and keeps the earlier panel's fields, wording and messages; it still passes `bottomPosition` so a new project goes to the bottom. `AdminPanel` shows it when Projects is chosen. The earlier Firebase projects store and spec are deleted, one line of the sign-in spec's notice loop is amended, and `CLAUDE.md` names the route. The SQL for `projects` was run on PostgreSQL by a throwaway script (impact.md SF-2); nothing in the suite runs it, so the owner's SIT check is the only test of the real database.

### 2.3 Data model

```ts
// src/lib/admin/projects.ts (existing; one export added)
type ProjectContent = {
  title: string; shortDesc: string; description: string[];
  tech: string[]; github: string; demo: string;
};
// new: projectShape(input: unknown): ProjectContent | null

// src/lib/server/listSql.ts (existing; the set grows by one name)
type ListTable = "experience" | "projects";
const LIST_TABLES: readonly ListTable[]; // ["experience", "projects"]
```

**Table** `projects` (created by the app, the same text as `experience` with the name changed):

| Column | Type | Meaning |
| ------ | ---- | ------- |
| `seq` | `bigint generated always as identity` | insertion order, breaks ties in `position` |
| `id` | `text primary key` | a version 4 UUID made by the server (`crypto.randomUUID()`) |
| `position` | `integer not null` | list order, lowest first; the screen sends the bottom position for a new project |
| `data` | `jsonb not null` | the six fields as `projectToData` writes them, normalised by `checkProject` |
| `updated_at` | `timestamptz not null default now()` | set on every write |

**Route** `/api/admin/projects/` (JSON; every response has `Cache-Control: no-store`):

| Method and query | Requester | Status | Body |
| ---------------- | --------- | ------ | ---- |
| `GET` | owner | 200 | `{ "entries": [ { "id": string, "position": number, "content": ProjectContent } ] }` ordered by `position` then insertion; `{ "entries": [] }` when empty; `content` is `projectFromData` of the stored value |
| `POST`, body `{ "content": ProjectContent, "position": integer }` | owner | 200 | `{ "id": string }` |
| `PUT ?id=<id>`, body `{ "content": ProjectContent }` | owner | 200 | `{ "updated": true }` |
| `PATCH`, body `{ "changes": [ { "id": string, "position": integer } ] }` | owner | 200 | `{ "moved": true }` |
| `DELETE ?id=<id>` | owner | 200 | `{ "deleted": true }` |
| `PUT`, `PATCH`, `DELETE` naming an id with no stored project | owner | 404 | `{ "error": "not-found" }`; nothing is stored |
| any, invalid body, id, position or changes | owner | 400 | `{ "error": "invalid" }`; nothing is stored |
| any | signed out | 401 | `{ "error": "not-signed-in" }` |
| any | signed in, not the owner (other account, or the owner's address with an unverified email) | 403 | `{ "error": "not-allowed" }` |
| any | owner, any database or unexpected failure | 503 | `{ "error": "unavailable" }` |

A position is a safe integer from -2147483648 to 2147483647. An id is a string matching `LIST_ID_PATTERN` (the shared pattern of `src/lib/admin/list.ts`).

**Stand-in file** (path = the part of `SUPABASE_DB_URL` after `stand-in:`): the key `projects` holds an array of `{ "id": string, "position": number, "data": <stored value> }` in insertion order; absent or not an array → empty. Writing `projects` keeps every other key (`profile`, `images`, `experience`, `unreachable`). The existing rules for `unreachable: true`, an unreadable file or a file that is not a JSON object stay.

### 2.6 Non-functional notes

- **Size**: one owner, a handful of projects; the whole list is loaded at once; no paging, no cap (Assumption 9). One connection per server instance, as today.
- **Time limits**: the browser gives up on a request after 15 seconds (`createHttpListStore`); the server's connect and query limits are the profile slice's.
- **Accessibility**: labels, `role="alert"` errors linked to their field with `aria-describedby`, and `role="status"` messages come from the existing `ListEditor`, `ProjectsEditor` and `formParts.tsx`; they are kept.
- **Theme and layout**: inline styles from the shared `formParts` token styles and the tokens `--surface-alt`, `--foreground`, `--muted`, `--accent-rose`, `--border`; no raw colour; values wrap.
- **Privacy**: no message, response or log carries an address, password, key or database error text (the `run` wrapper's rule, unchanged).
- **Cost**: Supabase free plan; one more small table.

### 2.7 Decisions made (do not revisit)

- **D-1 [human: intent §4]** The database is Supabase PostgreSQL through the built `postgres` library; no new dependency or setting name. **[auto]** No setting is added: the table is created on first use by the existing schema promise (decomposition Decision 11).
- **D-2 [auto]** The recipe of the experience spec § 2.4 is followed as written: add the table name to `ListTable`, add a route file under `src/app/api/admin/projects/` that builds `createListService` with the record's `shape`, `check`, `fromData` and `toData`, build the editor's store with `createHttpListStore("/api/admin/projects/", projectFromData, projectToData)`, delete the collection's Firebase store and spec. The route file is explicit and copies the experience route's `refusal()`, `reply()`, `readBody()` and `idOf()` helpers (experience D-4: a route factory would have to import `@/lib/auth` from a place the importer rules do not allow). `ListEditor` is used unchanged.
- **D-3 [auto]** Table `projects` with the columns of § 2.3, read `order by position, seq`; the whole record is in `data` (profile D-2, experience D-3).
- **D-4 [auto]** (Assumption 5) A new project goes to the bottom of the list: the editor keeps passing the existing `bottomPosition` as `newPosition`, so the screen sends `max position + 1` (0 for an empty list), and the server stores the position as sent (experience D-5). A direct request may place a project anywhere; only the owner can send one. The id of a new project is made by the server (`crypto.randomUUID()`).
- **D-5 [auto]** `projectShape`: the body's `content` must be a non-null, non-array object; `title`, `shortDesc`, `github` and `demo` are each a string or absent (absent counts as the empty string and `checkProject` then refuses an empty title); `description` and `tech` are each an array of strings or absent (absent is `[]`); any other kind returns `null`; extra properties are ignored.
- **D-6 [auto]** (Assumption 4) The link rule is the existing one: after trimming, a link that is not empty must match `^https?://` in any letter case (`checkProject`, `src/lib/admin/projects.ts`). A value of `https://` alone passes; no other URL validation is added, because the story says only "must start with".
