## 1. Business analysis — BA

### 1.1 Purpose

The owner adds, edits, reorders and deletes tech stack categories, and the items inside them, in the panel's "Tech stack" screen. They are kept in Supabase PostgreSQL, read and written only by the server and only for the owner. A category has a name and an ordered list of items; each item has a name and an icon, and the icon is either an image the owner uploaded in "Images" or a path to a file in the site's public files. This replaces the "Tech stack editor is not available yet." notice. It reuses the shared list pattern that `owner-manages-experience` built and `owner-manages-projects` and `owner-manages-certifications` reused (the list screen, the browser list store, the owner-only list route, the generic list service and the list SQL) and adds only what is particular to a category: its fields and rules, a table name, a route file, and an editor that puts a new category at the bottom, edits its items inside the form and offers the image picker built by `owner-uploads-images`. The category and its items are one stored record, so saving a category saves its items with it. The public Tech stack section keeps showing the tech stack that is in the repository.

### 1.2 Actors & preconditions

- **The owner**: signed in with the Google account whose verified email equals `ADMIN_EMAIL` (built by `owner-google-sign-in`). Sees the seven-item menu; Profile, Images, Experience, Projects and Certifications already open screens.
- **A signed-out visitor** and **a signed-in account that is not the owner**: refused on every request to the new route, including one sent without the panel. A signed-out visitor can open an uploaded image at its public address (intent §5; OVERVIEW §2 item 7), which is what an item stores when the owner picks an uploaded image.
- **The database**: Supabase PostgreSQL (`SUPABASE_DB_URL`, built by `owner-edits-profile`), empty at first; nothing is imported (story Assumption 15).
- **The image list**: the owner-only list of uploaded images (`/api/admin/images/`, built by `owner-uploads-images`), read by the browser beside the categories.

### 1.4 Data touched

- **Tech categories**: ordered records, each a category name and an ordered list of items (name and icon as text), with a position. The items are part of their category's record. No dates (Assumption 17).
- **The uploaded images**: read-only, through the existing owner-only image list, to fill each item's picker and to show an uploaded icon by its file name. This feature never writes an image.
- **The sign-in session**: read-only, to decide whether the requester is the owner.
- **The database setting** (`SUPABASE_DB_URL`): read on the server only; nothing new.

## 2. Technical specification — SA

### 2.1 Approach

This feature follows the reuse recipe of the experience spec (§ 2.4), as the projects and certifications specs did: a table name, a route file, an editor store, and the deletion of the collection's Firebase store and spec. `src/lib/server/listSql.ts` gains the name `tech_categories` in its closed set of table names, so the existing schema step also creates the table and the five existing database functions and the stand-in (already generic over the table name) serve it unchanged. A new owner-only route, `/api/admin/tech-stack/`, answers `GET`, `POST`, `PUT ?id=`, `PATCH` and `DELETE ?id=` through the existing `createListService`, which stays unchanged. The nested items live inside the category record's `data` (`{ category, tools: [ { name, icon } ] }`), so the list stores one record per category and the service needs no knowledge of items. The items are validated on the server by the two functions the service already takes: `techShape` (new, a wrong-kind check that walks the category and every item and drops extra properties) and `checkTechCategory` (existing, trimming and the rules for the category and for every item, now with one parameter). In the browser `TechStackEditor` swaps its Firestore store for `createHttpListStore("/api/admin/tech-stack/", techFromData, techToData)`, takes no props, keeps the earlier panel's fields, wording and messages, passes `bottomPosition`, and keeps the image picker it already has (`listImages`, `photoSelection`, `UploadedImage`) with its fallback when the images cannot be loaded. The icon rule changes in one way: the earlier check accepted an uploaded address only when it was in the image list the browser held, which a server cannot see, so both sides now use one rule that recognises the form of an uploaded image's public address (D-5). `AdminPanel` shows the screen when Tech stack is chosen. The earlier Firebase tech stack store and spec are deleted; the table-set pins in the projects and certifications specs, the sign-in spec's notice loop and the two Firebase file lists are amended in test bodies, and `CLAUDE.md` names the route. The SQL for `tech_categories` was run on PostgreSQL by a throwaway script (impact.md SF-2); nothing in the suite runs it, so the owner's SIT check is the only test of the real database.

// icon: an uploaded image's public address, or a repo path (starts with one "/")

**Table** `tech_categories` (created by the app, the same text as `experience` with the name changed):

| Column | Type | Meaning |
| ------ | ---- | ------- |
| `seq` | `bigint generated always as identity` | insertion order, breaks ties in `position` |
| `id` | `text primary key` | a version 4 UUID made by the server (`crypto.randomUUID()`) |
| `position` | `integer not null` | list order, lowest first; the screen sends the bottom position for a new category |
| `data` | `jsonb not null` | `{ "category": string, "tools": [ { "name": string, "icon": string } ] }` as `techToData` writes it, normalised by `checkTechCategory`; the items are only here, in their order, with no id of their own |
| `updated_at` | `timestamptz not null default now()` | set on every write |

**Route** `/api/admin/tech-stack/` (JSON; every response has `Cache-Control: no-store`):

| Method and query | Requester | Status | Body |
| ---------------- | --------- | ------ | ---- |
| `GET` | owner | 200 | `{ "entries": [ { "id": string, "position": number, "content": TechCategoryContent } ] }` ordered by `position` then insertion; `{ "entries": [] }` when empty; `content` is `techFromData` of the stored value |
| `POST`, body `{ "content": TechCategoryContent, "position": integer }` | owner | 200 | `{ "id": string }` |
| `PUT ?id=<id>`, body `{ "content": TechCategoryContent }` | owner | 200 | `{ "updated": true }` |
| `PATCH`, body `{ "changes": [ { "id": string, "position": integer } ] }` | owner | 200 | `{ "moved": true }` |
| `DELETE ?id=<id>` | owner | 200 | `{ "deleted": true }` |
| `PUT`, `PATCH`, `DELETE` naming an id with no stored category | owner | 404 | `{ "error": "not-found" }`; nothing is stored |
| any, invalid body, id, position or changes | owner | 400 | `{ "error": "invalid" }`; nothing is stored |
| any | signed out | 401 | `{ "error": "not-signed-in" }` |
| any | signed in, not the owner (other account, or the owner's address with an unverified email) | 403 | `{ "error": "not-allowed" }` |
| any | owner, any database or unexpected failure | 503 | `{ "error": "unavailable" }` |

A position is a safe integer from -2147483648 to 2147483647. An id is a string matching `LIST_ID_PATTERN` (the shared pattern of `src/lib/admin/list.ts`).

**Server-side validation of the nested items** (the one place the list service learns about items is its two functions, so the service is unchanged): the body's `content` goes through `techShape`, then `checkTechCategory`. `techShape` returns `null` unless `content` is a non-null, non-array object; `category` must be text or absent; `tools` must be absent or a list; every element of the list must be a non-null, non-array object whose `name` and `icon` are each text or absent; an absent value becomes `""` and an absent list becomes `[]`; anything else returns `null` for the whole body (answer 400). The result is a new object with exactly `category` and `tools`, each item a new object with exactly `name` and `icon`. `checkTechCategory` then trims and checks the category and every item (BR-05); the first failing request answers 400 with no detail and nothing is stored, so a category is stored whole or not at all.

**Icon rule** (`checkTechCategory`, after trimming): an empty icon is refused with `TECH_MESSAGES.iconRequired`; otherwise it must match the path form `^\/(?!\/)\S+$` or the uploaded-address form `^https?:\/\/[^\s/]+\/storage\/v1\/object\/public\/images\/\S+$` (both case-sensitive), else `TECH_MESSAGES.iconInvalid`. Messages are unchanged: `Category name is required`, `Category name must be 80 characters or fewer`, `Item name is required`, `Item name must be 80 characters or fewer`, `Icon is required`, `Icon path must start with "/"`. The error keys are `category`, `tools.<index>.name` and `tools.<index>.icon` (`itemErrorKey`).

**Stand-in file** (path = the part of `SUPABASE_DB_URL` after `stand-in:`): the key `tech_categories` holds an array of `{ "id": string, "position": number, "data": <stored value> }` in insertion order; absent or not an array → empty. Writing `tech_categories` keeps every other key (`profile`, `images`, `experience`, `projects`, `certifications`, `unreachable`). The existing rules for `unreachable: true`, an unreadable file or a file that is not a JSON object stay.

**Row text** (the screen, not stored; unchanged from the earlier panel): the first line is the category name; below it a group named `Items of <category>` holding one paragraph per item, `<name>: image <file name>` when the uploaded image list holds an image whose public address equals the icon, else `<name>: path <icon>`; a category with no items shows one paragraph `No items`.

### 2.6 Non-functional notes

- **Privacy**: no message, response or log carries an address, password, key or database error text (the `run` wrapper's rule, unchanged). An uploaded image's public address holds no token or key.
- **Cost**: Supabase free plan; one more small table; no new storage call (the picker reads the list the Images screen already uses).
