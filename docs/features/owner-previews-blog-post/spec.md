## 1. Business analysis — BA

### 1.1 Purpose

The owner writes a post's markdown body in the Blog posts screen and wants to see it rendered the way the blog shows a post, before saving, so formatting mistakes are caught without publishing or storing anything. A "Preview" button in the Add post and Edit forms swaps the fields for the body alone, rendered by the blog's own converter inside the blog's article styling, with a "Back to form" button that returns with nothing lost.

That behaviour already exists in the repository: `owner-manages-blog-posts` kept `PostPreview.tsx` and the Preview button on purpose, and `impact.md` records throwaway proofs that every central claim of this story holds today on the new stack (no server request, nothing stored, byte-identical to the public article). What is genuinely left is the proof and the clean-up: this feature writes the story's checks as a spec against the new stack, `e2e/owner-previews-blog-post.spec.ts`, and removes the Firebase-era `e2e/preview-blog-post.spec.ts`, which needs the Firestore emulator and cannot pass. It changes no production file, adds no dependency, setting or route, and changes nothing a visitor sees.

### 1.2 Actors & preconditions

- **The owner:** signed in with the Google account whose verified email equals `ADMIN_EMAIL` (built by `owner-google-sign-in`), on the "Blog posts" screen (built by `owner-manages-blog-posts`) in an Add post or Edit form.
- **A signed-out visitor** and **a signed-in account that is not the owner's:** never reach the screen, so never reach "Preview" (story Scenario 7).
- No hand-made precondition. Every row runs against the production build with the stand-in database file, a minted session cookie for the owner and no Google, Supabase or network service.

### 1.6 Out of scope

Showing the title, date, tags or cover in the preview, or previewing inside the blog's page layout, listing card or feed entry; a live side-by-side preview; uploading or previewing image files; a warning about unsaved changes; reading time, word count or any other measure of the body; a shareable preview link or a way for anyone but the owner to read a draft; cleaning raw HTML in the body (all from the story's Out of Scope and Deferred). Also out: any change to a production file, to `package.json`, `playwright.config.ts` or `scripts/**`, and the Firebase-era acceptance spec (left for `retire-firebase`).

## 2. Technical specification — SA

### 2.1 Approach

The preview is already built and correct: `PostPreview.tsx` converts the body in the browser with the blog's own `markdownToHtml` (imported from `@/lib/markdown`) and renders it in the blog's `PostBody` wrapper, `BlogPostsEditor.tsx` swaps it in for the fields and hides Save and Cancel through `ListEditor`'s `hideFormActions`, and it makes no request. This feature therefore edits no production file. It adds one spec file, `e2e/owner-previews-blog-post.spec.ts`, whose seventeen rows prove each story scenario and assumption against the production build with a minted owner session and the stand-in database file; two of the rows prove the "same pipeline" claim directly (the preview's HTML equals the public article's HTML for both repository posts, and a highlighted keyword has the blog's colour). It removes the Firebase-era `e2e/preview-blog-post.spec.ts` with `git rm` and removes the one line of `e2e/owner-manages-blog-posts.spec.ts` that expects it. One Step does all of it; the implementer's only code-side work is the removal, and it edits no production file.

## 3. BDD acceptance criteria — BA

```gherkin
# AC-01
Scenario: The preview shows a heading, a list, a table, a link and a code block as elements

  Then the preview shows the heading, the two list items, the table with its header cells and body cells, the link with its address and the code block

Scenario: The preview shows only the body
  Given the owner has filled the title, excerpt, date, slug and body of an Add post form
  When the owner chooses "Preview"
  Then the preview shows no title, no excerpt, no date and no level-1 heading
  And none of the form's fields is shown

# AC-03
Scenario: Previewing saves nothing
  Given the owner has filled an Add post form and chosen "Preview"
  Then no post is stored
  And "Entry saved" is not shown

# AC-04
Scenario: The code block is coloured with the blog's highlighting
  Given the owner previews a body with a fenced JavaScript code block
  Then the code block carries the blog's highlight classes
  And a keyword in it has the same colour as the same keyword in a published post
  And that colour differs from the colour of a number in it and from the colour of a paragraph

# AC-05
Scenario: Strikethrough, heading anchors and raw HTML render as the blog renders them
  Given the owner previews a body with a heading, struck-through text and an inline raw HTML element
  Then the heading holds a "#" link labelled "Link to this section" that points at the heading's id
  And the struck text is a deletion element and the raw HTML is a real element
  And the rendered body sits in the blog's prose container

# AC-06
Scenario Outline: The preview's markup equals the public article's markup
  Given the owner types the body of the repository post "<post>" into an Add post form
  When the owner chooses "Preview"
  Then the preview's rendered body is identical to the body of the public page for "<post>"

  Examples:
    | post                      |
    | building-portfolio-nextjs |
    | hello-world               |

# AC-07
Scenario: Save and Cancel are hidden while previewing

  When the owner chooses "Preview"
  Then "Save" and "Cancel" are not offered
  And "Back to form" is offered

Scenario: Back to form returns with everything as typed
  Given the owner has filled every field of the Add post form and chosen "Preview"
  When the owner chooses "Back to form"
  Then every field holds what was typed, and the body is exactly as typed
  And "Save" and "Cancel" are offered again

# AC-09
Scenario: Previewing again shows the changed body
  Given the owner has returned from a preview to the form
  When the owner changes the body and chooses "Preview" again
  Then the preview shows the changed body and not the earlier one

# AC-10
Scenario: A draft with an uploaded cover previews the body only
  Given the owner is adding a Draft post with an uploaded image as its cover and a cover alt text
  When the owner chooses "Preview"
  Then the preview shows the body
```
