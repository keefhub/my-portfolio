## 1. Business analysis — BA

### 1.1 Purpose

The owner writes blog posts in the panel and saves each as Draft or Published. Today the public blog still shows two posts written into the repository, and nothing the owner saves reaches visitors. This feature makes the blog page and every post address show what the owner saved as Published, and only after the owner chooses "Publish" (or the site is deployed). A new post must be readable at its own address with no code change, build or deployment. A draft must never reach a visitor. The two posts in the repository and the code that reads them are removed, in their own commit, so the owner re-enters them in the panel. RSS and the sitemap are the next slice and are not built here.

### 1.2 Actors & preconditions

- **Owner**: signed in with the owner's Google account; has the panel's "Blog posts" screen (built) and the "Publish" button with its owner-only check (built by the profile slice).
- **Visitor**: signed out, opens `/blog/` and `/blog/<slug>/`; sees only published content.
- Preconditions: the panel saves posts to the database with status Draft or Published (built: `owner-manages-blog-posts`); Publish renews the kept copies (built for the landing page: `owner-publishes-profile`).

## 2. Technical specification — SA

### 2.1 Approach

The blog list and each post page become kept pages that read the published posts on the server through one cached read of the whole published set, and declare `export const revalidate = false`, so only Publish or a deploy renews them. The post page is no longer limited to build-time slugs (`dynamicParams = false` goes): it renders an address on its first visit and keeps it. Because a never-opened address renders at that moment, the page must not read the live table; it reads the cached published set (a kept copy of the read, tagged and keyed by the database setting), so a post saved but not published is still not found (impact.md SF-2, proven at level 4). Publish adds one call after the landing page's: it expires that tag and revalidates the `/blog` layout, which renews the list and every post address (SF-1, level 4). A pure module turns stored records into the view type (published only, tolerant, sorted, reading time); a server module owns the cached read and the refresh. The not-found page is added at the site root with a link back. The two components gain a cover image and wrapping. The repository posts, their loader and the barrel's loader exports are deleted in their own commit, and RSS and the sitemap stop importing the loader (they list no post). Earlier specs and the standing documents are amended where this makes them false.

### 2.3 Data model

Nothing is stored or migrated. The read model (client-safe, in `src/lib/publicPosts.ts`):

```ts
export type PublicBlogPost = {
  slug: string;
  title: string;
  excerpt: string;
  date: string;        // "YYYY-MM-DD"
  tags: string[];
  featured: boolean;
  coverImage: string;  // "" or a "/..." path or an http(s) address
  coverAlt: string;
  readingTime: number; // whole minutes, at least 1
  content: string;     // the markdown body
};
```

It is assignable to `BlogPost` and `BlogPostLite` of `src/lib/blog/types.ts`, so the existing components take it unchanged. The stored record it reads is `StoredPost = { slug: string; published: boolean; data: unknown }` (`src/lib/server/database.ts:326`), where `data` holds `title`, `excerpt`, `date`, `tags`, `featured`, `coverImage`, `coverAlt`, `body`.

### 2.6 Non-functional notes

- Sized for one owner and a few posts a month: the published set is one kept entry (bodies included); no paging.
- A visitor's browser loads no database code; `src/lib/server/publicPosts.ts` is `server-only`.
- The not-found page for a post address is drawn by the browser (the response is 404 with the framework's error shell), so with JavaScript off the page is blank (SF-8, OQ-6).
