## 1. Business analysis — BA

### 1.1 Purpose

The Experience section of the landing page still shows five jobs and studies written into the code, while the owner already manages an Experience list in the panel. This feature makes the section show the saved entries, in the order the owner set, and only after the owner presses Publish. Saving or reordering changes nothing for visitors. With no saved entry the work-history timeline is not shown at all, and the rest of the page, including the Experience menu link, stays as it is. The entries written into the code are deleted.

### 1.2 Actors & preconditions

- **Owner**: signed in with the Google account whose verified email is `ADMIN_EMAIL`; has the Experience screen (built, `owner-manages-experience`) and the Publish button (built, `owner-publishes-profile`).
- **Visitor**: anyone; never signs in; sees the last published copy of the landing page.
- Precondition: the Publish route and the kept landing page of `owner-publishes-profile` exist (built).

## 2. Technical specification — SA

### 2.1 Approach

`src/app/page.tsx` already is a kept page (`revalidate = false`) that reads the published profile. It now also calls one new server read, `loadPublishedExperience()`, and renders the timeline only when the list is not empty. The Publish route is not changed: its owner check, its single profile read and its single `revalidatePath("/")` already renew the whole page, entries included. A client-safe module `src/lib/publicExperience.ts` holds the view type and a tolerant reader that turns stored records into entries; the server read adds the production-build guard and calls `readListRecords("experience")`. The timeline component stops holding data, takes the entries as props, returns nothing for an empty list, shows Description and Duration on the back of a card that has no detail lines, and wraps long words. The success message, the three earlier checks it or the component touch, and the standing documents are amended where this switch makes them false. This is the mechanism proven in the profile slice (D-01, D-04); nothing about the blog pages changes.

### 2.3 Data model

No stored data changes. The stored shape is the existing `ExperienceContent` of `src/lib/admin/experience.ts` (not imported by any public file):
`{ year: string; title: string; company: string; duration: string; description: string; details: string[] }`, stored as the `data` of a record `{ id, position, data }` of the table `experience`.

The new public view (`src/lib/publicExperience.ts`):

```ts
export type PublicExperienceEntry = {
  year: string;
  title: string;
  company: string;
  duration: string;
  description: string;
  details: string[];
};
export function publicExperienceFrom(records: readonly { data: unknown }[]): PublicExperienceEntry[];
```

The server read (`src/lib/server/publicExperience.ts`): `export async function loadPublishedExperience(): Promise<PublicExperienceEntry[]>`.

The timeline component: `export default function ExperienceTimeline(props: { entries: PublicExperienceEntry[] })`.

Publish response bodies are unchanged (`{"published":true}` 200, `{"error":"not-signed-in"}` 401, `{"error":"not-allowed"}` 403, `{"error":"unavailable"}` 503).

### 2.6 Non-functional notes

- Cost: one extra database read per renewal of the landing page; a personal site, one owner.
- Failure: database errors are reduced to a fixed message by `run()` in `src/lib/server/database.ts`; this feature adds no logging.
- Accessibility: the card keeps `role="button"`, `tabIndex={0}`, `aria-label` and `aria-expanded`; tokens only (`var(--…)`), no raw colour, no `dark:` variant.
- Security: nothing new reaches the browser except the entries' own text; no secret, setting name or owner email.
- The framework renews `/` on the first visit after Publish, so "within a minute" is met by the first visit (earlier feature's SF-2).
