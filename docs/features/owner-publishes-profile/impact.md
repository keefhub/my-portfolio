**Risks**

1. A visitor's request that regenerates `/` reads the database at that moment, so it shows what is saved *then*, not what was saved when the owner pressed Publish. Likelihood low (one owner, a few saves a month) × cost low (the page shows a newer save). Accepted by the intent (§3 "a separate published copy" is a non-goal). Carried: Decision D-18.
2. If the database is unreachable when the first visitor after a Publish arrives, the regeneration fails. Whether the framework then serves the previous copy is **unproven** in this feature (the outage slice owns the proof). Publish itself reads the database before invalidating (TS-01), which makes this window small. Carried: Open Question OQ-1 and Step 2's Stop-if.
3. A code deploy while the database is unreachable fails the build, because a set but unreachable setting makes the page read throw. Accepted by the intent (§4 "that deploy may fail and the previous one stays live"). Carried: Decision D-06.
4. The blog pages' footer shows no name or links, and their menu still shows "About" (even with no profile), until the blog slice feeds them. Likelihood certain × cost low. Carried: Decision D-08 and Open Question OQ-2.
5. `AdminPanel.tsx` gains a button; specs that count the panel's buttons or text in the signed-in state could change. Searched: `git grep -n "getByRole(\"button\")" e2e/` finds only `menu(page).getByRole("button")` scoped to the section menu (`owner-edits-profile.spec.ts:931`), so the new button, placed outside the `Admin sections` navigation, does not change those counts.

- `src/app/blog/layout.tsx` is unchanged: `Header` and `Footer` props are optional, so the blog call compiles and renders as before.
