## 1. Business analysis — BA

### 1.1 Purpose

The owner has a Profile screen that saves to the database, but visitors still see text written into the code. This feature makes the landing page's hero, About section, footer and "About" menu link show the saved profile, and adds one **Publish** button to the panel. Saving changes nothing for visitors; pressing Publish makes the next visit show what is saved. Only the signed-in owner can publish, a failed publish changes nothing, and with no saved profile the profile sections are hidden and the rest of the page still renders.

### 1.2 Actors & preconditions

- **Owner**: signed in with the Google account whose verified email is `ADMIN_EMAIL`; has the Profile screen (built, `owner-edits-profile`).
- **Visitor**: anyone; never signs in; the public read looks at nothing about them.
- **Other signed-in account** and **signed-out requester**: can send a request to the publish address; always refused.
- **Two sites**: SIT and live each have their own database and their own kept copy of the page.
- Preconditions: the owner sign-in, the profile editor and its route, and the image library are built and committed (impact.md § Domain map).

### 1.4 Data touched

- The saved profile record (name, headline, About paragraphs, photo address, email, resume address, social links): **read** by the public page and by the publish request; never written by this feature.
- The kept copy of the landing page (and nothing else): marked out of date by a publish.
- Nothing is written to a database, a file or a cookie by this feature.

### 1.5 Edge cases & negative paths

- Publish pressed while signed out, as another Google account, from the panel's address, directly [in spec].
- Database unreachable at Publish [in spec]; network lost after the panel loaded [in spec, Assumption 17].
- Double press [in spec]; Publish while nothing is saved [derived, BR-20]; a GET to the publish address [derived, BR-21a]; a body or a malformed body on the publish request [in spec, Assumption 22 / BR-21b].
- Profile with only Name and Headline: no photo, email, resume, social row, About section, About menu link, hero "About Me" button or scroll cue [in spec, Assumption 9; BR-14e derived].
- Saved record present but its Name empty (a damaged record): treated as no profile [derived, Decision D-10].
- Social link with a lookalike host, an `http://` address, an uppercase host, or an empty Label [derived, BR-04d/e].
- A saved change made after Publish and before the first visitor: the visitor sees what is saved at that moment (Decision D-18) [derived].
- 375-pixel screen with an unbroken 80-character name [in spec, Assumption 10].
- Time zones, invalid free text and navigation away: N/A (story Assumption 22).

### 1.6 Out of scope

Publishing experience, tech stack, projects, certifications or blog posts; keeping content during an outage across every public page (the outage slice); a one-time import; a preview, history, rollback or scheduled publish; a separate published copy; a rebuild-based publish or any new setting, dependency or service; refreshing the blog pages (Decision D-08); the site metadata in `src/app/layout.tsx`.

## 2. Technical specification — SA

### 2.1 Approach

The landing page stays a static, kept page but its data comes from the database: `src/app/page.tsx` becomes an async server component that calls `loadPublishedProfile()` and declares `export const revalidate = false`, so the framework keeps the page and renews it only on demand. A new owner-only `POST /api/admin/publish/` runs `getPanelState()` first, then reads the profile once to prove the database is reachable, then calls `revalidatePath("/")` and replies; a read failure replies 503 and invalidates nothing. The hero, About, footer and header become presentational: they take the published profile (or `showAbout`) as props and render nothing for an empty field. A small client-safe module holds the view type and the icon rule. The panel gets one `PublishButton` under the "Admin" heading. Earlier specs and the standing docs are amended where this switch makes them false. This is the proven design of impact.md SF-2 (level 4); the blog pages are deliberately left alone (SF-3).

### 2.3 Data model

No stored data changes. The stored profile shape is the existing `ProfileContent` (`src/lib/admin/profile.ts`): `{ name, headline, about: string[], photo, email, resumeLink, socialLinks: {label, url}[] }`. The new public view type (`src/lib/publicProfile.ts`):

```ts
export type SocialKind = "github" | "linkedin" | "mail" | "link";
export type ContactKind = SocialKind | "file";
export type PublicSocialLink = { label: string; url: string; kind: SocialKind };
export type ContactLink = { kind: ContactKind; href: string; label: string };
export type PublicProfile = {
  name: string; headline: string; about: string[]; photo: string;
  email: string; resumeLink: string; socialLinks: PublicSocialLink[];
};
```

Publish response bodies: `{"published":true}` (200), `{"error":"not-signed-in"}` (401), `{"error":"not-allowed"}` (403), `{"error":"unavailable"}` (503). No other field.

- Owner sign-in (`getPanelState`, `src/lib/auth.ts`): built (commit series `owner-google-sign-in`, present in HEAD history).

- `next/cache` `revalidatePath` and `lucide-react` icons `Github`, `Linkedin`, `Mail`, `FileText`, `Link`: installed (Next 16.2.6, lucide-react 0.503.0). No new package.
- Later slices (experience, tech stack, projects, certifications, blog posts, feeds, outage, repo-content): unbuilt; this feature leaves seams for them (one Publish button, one read module pattern) and nothing more.

### 2.6 Non-functional notes

- Performance and cost: one database read per Publish and one per regeneration; a personal site, one owner.
- Failure: database errors are reduced to a fixed message by `run()` in `src/lib/server/database.ts`; this feature adds no logging of its own.
- Accessibility: Publish is a native `<button>`; status and alert roles; tokens only; focus ring left to the browser default.
- Security: owner check first; no outbound request; no secret, address or owner email in any response, page or bundle. `SameSite=Lax` session cookie (impact.md SF).
- The framework refreshes `/` on the first visit after Publish, blocking (SF-2), so "within a minute" is met by the first visit.
