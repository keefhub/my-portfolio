**Risks**

- **R-1 A test stand-in ships in the production bundle** (`src/lib/server/storageStandin.ts`). Likelihood low, cost low: it runs only for a `SUPABASE_URL` that starts with `stand-in:`; on Vercel the owner would have to type that by hand, and the result is a failing upload, not an exposure. Carried as Decision D-5 and checked by E2E-12 (a real address takes the real path).
- **R-2 Supabase Storage is never run by automation** (decomposition Open finding 1). The HTTP contract is read from the library's source (SF-5) and enforced against a fake server that the test process runs (E2E-12, E2E-13); the hosted service's behaviour is unproven. Carried to E2E-36 and OQ-1.
- **R-3 A browser upload without the project's public key** may be refused by the hosted gateway (SF-5). The library's own signed upload sends its client's headers; ours sends only `content-type`. Likelihood low, cost one SIT round: the fix would add a public-key setting name, which this run may pick under intent §4. Carried to OQ-2.
- **R-4 The service key is powerful.** `SUPABASE_SERVICE_ROLE_KEY` bypasses every access rule of the project, the database included. It is read in one server-only module, sent only in request headers, never logged and never returned (SF-3, SF-10). Accepted: Storage offers no narrower key for this use. Carried as TS-09 and E2E-13.
