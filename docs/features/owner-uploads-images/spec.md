## 1. Business analysis — BA

### 1.1 Purpose

The owner uploads PNG, JPEG, WebP or SVG images of at most 5 MB in the panel's Images screen, sees them listed newest first with their sizes, copies an image's public address, picks an uploaded image as the profile photo, and deletes an image after confirming. Only the owner can upload or delete; anyone can open an image by its address. It is the first feature that uses Supabase Storage: the list is kept in the database (a table), the files in one public-read bucket, and the browser sends each file straight to Storage through a one-file upload address that only the server can issue. When the database or the file storage cannot be reached the Images screen and the Profile screen's image list say so, and nothing else in the panel, in sign-in or on the public site is affected. Public pages keep showing what is in the repo.

### 1.2 Actors & preconditions

- **The owner**: signed in with the Google account whose verified email equals `ADMIN_EMAIL` (sign-in slice, commit 61abc37). Sees the seven-item menu; "Profile" already opens its screen (profile slice, commit 9c66c1a) and "Images" opens its screen with this feature.
- **A signed-out visitor** and **a signed-in account that is not the owner**: refused on every upload, register and delete request, also when sent without the panel. Both may open an uploaded image by its address.
- **The database** (Supabase PostgreSQL, `SUPABASE_DB_URL`) holds the list; **file storage** (Supabase Storage, `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`) holds the files. Both start empty; nothing from the earlier panel is imported (story Assumption 25, intent §8).
- The notice "Images editor is not available yet." is replaced for Images only (story Assumption 5 keeps the earlier screen's wording).

### 1.4 Data touched

- **The image list**: one entry per image — its identifier (which is also its file's name in storage), the file name as the owner's computer gave it, the declared type, and the size in bytes. No dates are shown (Assumption 26). Newest first.
- **The stored files**: one object per entry in the bucket `images`; their public addresses are built when the list is answered.
- **The profile's photo**: a text value that may now be an image's public address (profile slice; the stored shape is unchanged).
- **The sign-in session**: read-only, to decide whether the requester is the owner.
- **The settings**: `SUPABASE_URL` (the project's address, read as its origin), `SUPABASE_SERVICE_ROLE_KEY` (secret), both read on the server only; `SUPABASE_DB_URL` as before.

## 2. Technical specification — SA

### 2.1 Approach

The server gets two owner-only route handlers under `/api/admin/images/`: one that checks a file's details and issues a one-file upload address (`POST /api/admin/images/upload/`), and one that lists (`GET`), registers a stored file (`POST`) and deletes (`DELETE ?id=`). Each asks `getPanelState()` first, answers with fixed JSON and fixed status codes, and maps every storage or database failure to `503 {"error":"unavailable"}`. Behind them are small server-only modules: the image SQL (one table), the database module extended with four image functions, the storage module (the only reader of the two storage settings; plain `fetch` to Supabase Storage, or a stand-in directory when the address starts `stand-in:`), and the image store that orders the operations. The browser sends the file itself to the upload address with `PUT` (a Vercel function cannot receive 5 MB, decomposition Decision 10), then asks the server to register it; the server confirms the file is really stored and within the rules before it lists it. Shared rules (types, limits, the id pattern, the body check) live in one client-safe module so the panel, the server and the tests apply the same ones. The Images screen and the Profile screen's "Uploaded image" choice call the routes through one client module. The stand-in follows the profile slice's precedent: values that start with `stand-in:`, selected only by the test run's environment, with the tests answering the browser's calls to the stand-in storage host themselves; a fake Storage server run by the test process exercises the real fetch code. The SQL was proven on PostgreSQL by a throwaway script and the HTTP calls were read from `@supabase/storage-js`; nothing in the suite runs the real services, so the owner's SIT check is the only test of them (decomposition Open finding 1).

### 2.3 Data model

```ts
// src/lib/admin/images.ts (additive in Step 1; the old ImageRecord and storagePathFor go in Step 5)
type UploadedImage = { id: string; name: string; url: string; contentType: string; size: number };
type ImageInput = { name: string; type: string; size: number };
type ImageRefusal = "invalid" | "empty" | "wrong-type" | "too-big";
type ImageInputCheck = { ok: true; value: ImageInput } | { ok: false; reason: ImageRefusal };
```

**Table** (created by the app; the exact text is in Step 2):

| Column | Type | Meaning |
| ------ | ---- | ------- |
| `seq` | `bigint generated always as identity` | insertion order; newest first is `order by seq desc` |
| `id` | `text primary key` | `<uuid>.<ext>` with `<ext>` one of `png`, `jpg`, `webp`, `svg`; also the object's name in the bucket |
| `name` | `text not null` | the file name, trimmed, 1 to 255 characters |
| `content_type` | `text not null` | one of the four allowed types |
| `size` | `integer not null` | bytes, 1 to 5,242,880 |
| `created_at` | `timestamptz not null default now()` | not shown anywhere |

**Bucket**: id `images`, public read, `file_size_limit` 5242880, `allowed_mime_types` the four types. **Public address** of an image: `<origin of SUPABASE_URL>/storage/v1/object/public/images/<id>`; stand-in: `https://stand-in.invalid/storage/v1/object/public/images/<id>`. Never stored; built when the list is answered.

**Routes** (JSON, every response has `Cache-Control: no-store`):

| Method and path | Requester | Status | Body |
| --------------- | --------- | ------ | ---- |
| `GET /api/admin/images/` | owner | 200 | `{ "images": UploadedImage[] }`, newest first |
| `POST /api/admin/images/upload/` body `{ name, type, size }` | owner, passes the rules | 200 | `{ "id": string, "uploadUrl": string }` (stores nothing) |
| same | owner, fails the rules | 400 | `{ "error": "invalid" \| "empty" \| "wrong-type" \| "too-big" }` |
| `POST /api/admin/images/` body `{ id, name, type, size }` | owner, file stored and within the rules | 200 | `{ "image": UploadedImage }` |
| same | owner, body fails the rules or the id is not an id the server issues | 400 | `{ "error": "invalid" \| "empty" \| "wrong-type" \| "too-big" }` |
| same | owner, nothing stored under that id | 400 | `{ "error": "missing" }` |
| same | owner, stored file outside the rules (its object is removed) | 400 | `{ "error": "rejected" }` |
| `DELETE /api/admin/images/?id=<id>` | owner, entry existed | 200 | `{ "deleted": true }` |
| same | owner, no entry with that id | 404 | `{ "error": "not-found" }` |
| same | owner, `id` missing or not an id the server issues | 400 | `{ "error": "invalid" }` |
| any of the above | signed out | 401 | `{ "error": "not-signed-in" }` |
| any of the above | signed in, not the owner | 403 | `{ "error": "not-allowed" }` |
| any of the above | owner, any storage, database or unexpected failure | 503 | `{ "error": "unavailable" }` |

**Storage HTTP calls** (real mode; `<base>` is the origin of `SUPABASE_URL`; the key is sent as both `apikey: <key>` and `authorization: Bearer <key>` except where noted):

| Purpose | Call |
| ------- | ---- |
| Bucket exists? | `GET <base>/storage/v1/bucket/images` |
| Create the bucket (when the read answered 400 or 404) | `POST <base>/storage/v1/bucket` with `content-type: application/json` and exactly `{"id":"images","name":"images","public":true,"file_size_limit":5242880,"allowed_mime_types":["image/png","image/jpeg","image/webp","image/svg+xml"]}`; `200` or `409` is success |
| One-file upload address | `POST <base>/storage/v1/object/upload/sign/images/<id>` with `content-type: application/json`, body `{}` and `redirect` left at its default; the answer's `url` must start with `/object/upload/sign/images/<id>?token=`; the address given to the browser is `<base>/storage/v1` followed by that `url` |
| Stored size and type | `HEAD <base>/storage/v1/object/public/images/<id>` with `accept-encoding: identity` and no key; `200` gives `content-length` and `content-type`; `400` and `404` mean "not stored" |
| Remove the object | `DELETE <base>/storage/v1/object/images` with `content-type: application/json` and `{"prefixes":["<id>"]}`; any `2xx` is success |

Every call has `cache: "no-store"` and `AbortSignal.timeout(5000)`.

**Stand-in files.** Database stand-in (the profile slice's file, `SUPABASE_DB_URL` after `stand-in:`): a JSON object `{ "profile"?: …, "images"?: StoredImage[], "unreachable"?: true }` where `StoredImage = { id: string; name: string; contentType: string; size: number }`, newest first; an `images` value that is not an array counts as empty and an element that is not that shape is skipped. Storage stand-in (directory = `SUPABASE_URL` after `stand-in:`): absent directory → reachable and empty; object `<id>` is the file `<dir>/<id>` and its type is the text of `<dir>/<id>.type`; a file named `unreachable` in the directory makes every operation fail. Upload address in stand-in mode: `https://stand-in.invalid/storage/v1/object/upload/sign/images/<id>?token=stand-in-token`.

**Log line**: `[storage] <bucket|sign|stat|remove> failed <code>`, where `<code>` is `HTTP_<n>` for a failure that carries an integer `status` from 100 to 599, else the failure's string `code` when it matches `^[A-Za-z0-9_]{1,20}$`, else the same test on `cause.code`, else `unknown`.

### 2.7 Decisions made (do not revisit)

- **D-1 [human: intent §4]** Supabase Storage (free plan) holds the uploaded images. **[auto]** One bucket with the id `images`, created by the app (BR-18a) with `public: true`, `file_size_limit: 5242880` and `allowed_mime_types` the four types, as the decomposition's "New surface" says. Public read is what lets anyone open an address (Assumption 1).
- **D-2 [human: intent §4]** Supabase storage connection settings; the agent picks the names. **[auto]** Two new names: **`SUPABASE_URL`** (the project's address; only its origin is used, so a trailing slash or path is harmless; not a secret but set in Vercel with the others) and **`SUPABASE_SERVICE_ROLE_KEY`** (the project's service key; a secret). Both are read in `src/lib/server/storage.ts` only. `SUPABASE_DB_URL` is reused for the list (the database). Why two: an address and a key are different values; the key cannot be derived from anything already set, and the project address cannot be read reliably out of the database string (the pooler form carries the project reference in its user name, the direct form in its host, and a mistyped one in neither). Rejected: one combined setting (it would put a secret into a value people read as an address), S3-style access keys (two more names), `NEXT_PUBLIC_*` names (they reach the browser), and a library that reads its own names (`@supabase/supabase-js` is not approved and the gate forbids it). The names are the conventional ones for these two values. Listed for the pull request: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (new here); `SUPABASE_DB_URL` (reused). The owner sets them in Vercel for Production and SIT; the value of the key is whatever Supabase's dashboard calls the service role or secret key.
- **D-3 [auto]** (decomposition Decision 10) Upload is three calls: the server issues a one-file upload address after the rules (`POST …/upload/`), the browser sends the file to it with `PUT` and only a `content-type` header, and the browser then asks the server to register it (`POST …/images/`). Why: a free-plan Vercel function cannot receive a 5 MB body, and the storage key stays on the server. The token inside the upload address is the one credential the browser sees (BR-14d); it opens one object path only (SF-5).
- **D-4 [auto]** (decomposition Decision 11) Storage is called over its HTTP interface with `fetch`; no library, no new dependency. The calls are those of `@supabase/storage-js` 2.119.2, read from its source in a scratch directory (impact.md SF-5); the package is not installed and must not be added.
- **D-5 [auto]** (decomposition Decision 7) The storage stand-in follows the database stand-in's precedent: a `SUPABASE_URL` that starts with `stand-in:` followed by a directory path selects it, the test run's value comes from `playwright.config.ts`, and no setting name is added. The browser's own calls to the stand-in storage host (`https://stand-in.invalid`) are answered by the tests with `context.route`, so the repo has no test-only route. A value that is exactly `stand-in:` (nothing after it) is an unavailable setting, never passed to `fetch`. The real fetch code is exercised by E2E-12 and E2E-13 against a fake Storage server that the test process runs on a local port, using a `SUPABASE_URL` that is an ordinary `http://127.0.0.1:<port>` address. Rejected: a test-only HTTP route (production surface), a fake server started by the Playwright configuration (new harness), an unapproved mock package. Cost: the suite never talks to Supabase (R-2).
- **D-6 [auto]** The list is the table `images` (BR-18b); the entry's `id` is `<uuid>.<ext>` and is also the object's name, so an address is never built from the file name (BR-06) and the extension is the type's (`png`, `jpg`, `webp`, `svg`). The address is built from `SUPABASE_URL` when the list is answered, not stored, so one table can serve two deployments. `created_at` exists for the owner's own queries and is never shown. Order is `seq desc`, not the time, so two uploads in the same millisecond keep their order.
- **D-7 [auto]** Image SQL lives in `src/lib/server/imageSql.ts`, not in `sql.ts`: an earlier test requires that `sql.ts` contains none of `drop `, `delete `, `truncate `, and the delete statement is needed here. The statements are the ones proven on PostgreSQL (impact.md SF-4).
- **D-8 [auto]** Statuses and bodies are those of § 2.3. Refusals reuse the profile route's: `401 {"error":"not-signed-in"}` for no valid session, `403 {"error":"not-allowed"}` for a valid session that is not the owner, `503 {"error":"unavailable"}` for any failure. The owner check runs before the body is read and before any database or storage call, so a refusal never depends on either (BR-04j). A body that cannot be parsed counts as `undefined` and is `invalid`.
- **D-9 [auto]** Order of operations. *Issue an address*: rules → bucket ready → address; nothing is stored or listed. *Register*: rules (the same function) and id pattern → bucket ready → stored size and type → rules on those → insert the entry. *Delete*: entry exists? → remove the object → delete the entry. The file goes first so that a storage failure leaves a listed entry the owner can delete again (BR-08h), instead of an unlisted file that anyone with the address can still open. Deleting an entry whose file is already gone succeeds. A registration that finds the file outside the rules removes the object once, ignoring a failure of that removal; any other failure leaves leftovers, which are never listed (story Deferred).
- **D-10 [auto]** Register trusts what storage reports. Its body repeats the file's name, type and size. When the stored size is reported it replaces the declared one, and when the stored type is reported it must equal the declared type; when a value is not reported the declared one is used. The result must pass the same rules (non-empty, at most 5,242,880 bytes, an allowed type), and the extension of the type must equal the extension of the id. Otherwise: `rejected`, and the object is removed. A second registration of the same id changes nothing and answers the same entry (`on conflict (id) do nothing`).
- **D-11 [auto]** One schema step for both tables: the existing once-per-process schema run in `database.ts` runs the profile statements and then the image statements, before the first read or write of either (R-8). A failure is not remembered, as before.
- **D-12 [auto]** Real mode: the bucket check runs once per process per pair of settings and a failure is not remembered; stand-in mode checks reachability on every call, so a test can switch storage off and on. If the bucket read answers 400 or 404 the bucket is created; `200` or `409` from the create is success; `401`, `403`, `5xx` and a network failure are failures.
- **D-13 [auto]** The stored size and type come from a `HEAD` of the public address that asks for no compression, with no key (the bucket is public). `400` and `404` mean "not stored". A missing `content-length` or `content-type` falls back to the declared value (D-10). This avoids the key on a public read and an authenticated metadata call whose field names are not proven (impact.md SF-6).
- **D-14 [auto]** Delete carries its id in the query (`?id=`), not in a body, so no proxy can drop it. The id must match the id pattern, so the object name is never taken from free text.
- **D-15 [auto]** Storage calls carry the key in both `apikey` and `authorization: Bearer` (accepting either key form the owner may hold is unproven, OQ-3), except the public `HEAD`. Failures are logged and thrown as one fixed error; the response body of a failed call is never read into a message or log (BR-14c).

The code lets the owner diagnose SIT (`HTTP_401` for a wrong key, `HTTP_404`, and for a refused connection `ECONNREFUSED` or `unknown`, whichever the fetch error's `cause.code` gives when it passes the allow-list; impact.md SF-3 records only one scratch run's observation, not a guarantee) and is not text of Storage's message.
