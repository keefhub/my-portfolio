## 1. Business analysis — BA

### 1.1 Purpose

The owner writes a post's markdown body in the Blog posts form and wants to see it the way the blog will show it before saving, to catch formatting mistakes without publishing or committing anything. A "Preview" control on the post form (adding or editing) swaps the form's fields for the body rendered as the blog renders it: headings with their anchors, lists, tables, links, strikethrough, raw HTML as real elements, and code blocks highlighted with the blog's colours, inside the blog's own prose styling, following the panel's light or dark theme. It shows the body only (no title, date, tags or cover, no site header or footer). "Back to form" returns to the form with everything typed unchanged. Preview never writes to the database, validates nothing and shows "Nothing to preview yet" for a blank body. On a 375-pixel screen a wide table and a long code line stay reachable by scrolling inside the preview, never by scrolling the page. Public pages are untouched: the same content, and none of the preview code and no Firebase library.

### 1.2 Actors & preconditions

- **Owner:** the single signed-in Google account that reaches the allowed screen and the Blog posts editor (`manage-blog-posts`). Preview exists only inside that editor's Add and Edit forms.
- **Other account / visitor / unfilled account:** never reach a form. A non-owner never sees the editor; the rules at `firestore.rules:43` refuse a list that could include drafts to everyone but the owner, so for the unfilled account the editor shows the load failure and no Add control, and no form or Preview can be reached.
- No precondition met by hand beyond those of `manage-blog-posts` (intent §7). Every row runs against the local emulators.

## 2. Technical specification — SA

### 2.1 Approach

The blog's own converter, `markdownToHtml`, imports only the unified, remark and rehype packages and nothing server-only, but CLAUDE.md invariant 3 (enforced by `scripts/check-task.sh` as a path rule) lets a client component import from `@/lib/blog` through `@/lib/blog/types` only. So its body moves to a shared module outside the blog folder, `src/lib/markdown.ts`, and `src/lib/blog/markdown.ts` becomes a one-line re-export of it: every server caller (the barrel, the blog build) is unchanged, and the preview imports `@/lib/markdown`, so it renders exactly what the blog renders, through the same single set of plugins. The blog article's prose wrapper is extracted into a small shared component, `PostBody`, which `BlogArticle` and the preview both use, so the prose classes live in one place. A new client component `PostPreview` shows a "Back to form" button, then either "Nothing to preview yet" or the converted body inside a horizontally scrollable box. The Preview control lives in `BlogPostsEditor`: it holds one `previewing` flag, shows `PostPreview` in place of the form's fields while it is on, and tells `ListEditor` (through one new optional prop, `hideFormActions`) to hide Save and Cancel meanwhile. The form's draft stays in `ListEditor`, so returning loses nothing and nothing is written. No new package, route, token, stylesheet rule or stored field.

### 2.6 Non-functional notes

- Static export holds: no route, server code or generated param is added. `PostPreview` is a client component reached only through `BlogPostsEditor` (itself reached only through `AdminPanel`, imported only by `src/app/bright-warm-greenhouse/page.tsx`), so the converter's code lands in the owner panel's chunk and in no public page (E2E-10).
- Invariant 3: the preview imports `@/lib/markdown` (a pure module outside `src/lib/blog`); it never imports `@/lib/blog` in any form (the barrel, `posts`, `markdown`, `rss`), or `server-only`. Invariant 4: no date is shown. Invariant 6: `images.unoptimized` is untouched; no `<img` is written (an image in a body renders as a plain element from the converter's HTML).
- Raw HTML in a body renders as written, as on the blog (story Assumption 4). The only place that can write a body is the owner's form, so this is the owner viewing their own text; a `<script>` inserted through `dangerouslySetInnerHTML` does not run. No `rehype-sanitize` (story Out of Scope).
- `dangerouslySetInnerHTML` is moved, not added: its single use today is `BlogArticle.tsx:80`; it moves into `PostBody.tsx`, which both the blog and the preview use (D-05). `git grep -l dangerouslySetInnerHTML -- src` afterwards lists `src/app/components/blog/PostBody.tsx` and `src/app/layout.tsx` only (E2E-08).
- No `eslint-disable`, `@ts-ignore` or `@ts-nocheck` line is added; the conversion sets state only after an `await`, never synchronously in the effect body (`react-hooks/set-state-in-effect`).
- None of the new files holds the word `email` (`admin-sign-in` E2E-15 and `admin-owner-only-access` E2E-20 search the admin sources for it).
- A conversion that throws is handled with an alert line (D-10). No input is known to make the converter throw (impact.md Safety facts: an unknown fence language, unclosed tags and an unfinished table all convert), so this path has no row.
- Accessibility: the preview is a `section` named "Post preview"; "Back to form" and "Preview" are native buttons; the blank message is a `role="status"` paragraph.

## 3. BDD acceptance criteria — BA

```gherkin
# AC-01
Scenario: A body with a heading, a list, a table, a link and a code block previews as the blog shows them, and the preview shows the body only
  Given the owner is adding a post and has typed a title, an excerpt, a date, a slug and a body holding "## Preview heading", a two-item bulleted list, a two-column table, a link and a fenced js code block
  When the owner chooses "Preview"
  Then the preview shows a level-2 heading, a list of two items, a table with its header and its row, a link to the typed address and the code
  And the preview shows none of the title, the excerpt or the date, and has no level-1 heading
  And nothing is stored and "Entry saved" is not shown

# AC-02
Scenario: The preview uses the blog's features, container and highlight colours
  Given the owner is adding a post whose body has a heading, struck-through text, raw HTML and a fenced js code block
  When the owner chooses "Preview"
  Then the heading carries an anchor link "#" labelled "Link to this section" that points at the heading
  And the struck-through text and the raw HTML show as real elements
  And the rendered body sits in the blog's prose container
  And the code block is highlighted, and its highlighted word has the colour the same word has in a published post

# AC-03
Scenario: The owner returns to the form with the typed values unchanged
  Given the owner has filled every field of the Add form and chosen "Preview"
  Then "Save" and "Cancel" are not offered
  When the owner chooses "Back to form"
  Then every field holds what was typed, the body exactly as typed, and "Save" and "Cancel" are offered again
  And after the owner changes the body and chooses "Preview" again, the preview shows the changed body
  And nothing is stored

# AC-04
Scenario: Edits to a saved post are previewed without being saved
  Given a post "Why I moved to static export" is saved with the body "First draft" and the list offers no "Preview"
  And the owner has opened it and changed the body to "Second draft"
  When the owner chooses "Preview"
  Then the owner sees "Second draft" rendered and not "First draft"
  And after the owner returns, leaves with "Cancel" and opens the post again, the body is "First draft" and the stored post is unchanged

# AC-05
Scenario Outline: A blank body shows a message and a way back
  Given the owner is adding a post whose body is <body> and whose other fields are empty
```
