## 1. Business analysis — BA

### 1.1 Purpose

The owner uses the admin panel on two separate environments: SIT, where changes are tried, and production, the live site. Today the panel cannot sign in anywhere (the committed web settings are placeholders) and it knows only one Firebase project. The feature makes the panel pick the project that matches the address it is opened on, gives each environment its own owner ID, and makes the `develop` pipeline publish the security rules to SIT while `master` keeps publishing them to production. Nothing the visitor sees changes.

### 1.2 Actors & preconditions

- **Owner** (Keith): signs in with Google on SIT and on production. Each project gives the owner a different user ID, known only after the first real sign-in there.
- **Another signed-in account**: can open the panel, cannot save, upload or delete.
- **Public visitor**: reads the home page, blog list and posts; must load no Firebase code and see no change.
- **Pipeline**: `develop` pushes deploy to SIT, `master` pushes to production, each with its own GitHub environment and `FIREBASE_SERVICE_ACCOUNT`.
- Preconditions: pull request #3 (`ci/sit-and-prod-pipeline`) is merged into this branch's history; the SIT project, its web app, database and storage exist; both projects have Google sign-in on and their addresses authorised (owner's console tasks, intent §7).

### 1.4 Data touched

No stored content is created or changed. Business terms: the web settings of three targets (production, SIT, local stand-ins), two owner user IDs (placeholders at ship), the same two rules files deployed to two projects. SIT starts empty (Assumption 11); production is untouched (Assumption 12).

### 1.5 Edge cases & negative paths

- `[in spec]` `www.thegoldenpothos.xyz` and `thegoldenpothos.xyz.example.com` count as SIT (BR-03).
- `[in spec]` A hosting preview link whose name contains the production project ID counts as SIT (BR-03).
- `[in spec]` An unfilled owner ID on either environment: nobody saves (BR-10, BR-11a, BR-11b).
- `[in spec]` A different account on either environment is refused (BR-12, BR-13).
- `[derived]` `thegoldenpothos.dev`, `www.thegoldenpothos.dev`, a trailing-dot `thegoldenpothos.xyz.`, an upper-case `THEGOLDENPOTHOS.XYZ`, an empty host name, `127.0.0.2`, `localhost.example.com` and `127.0.0.1.example.com` are all unlisted and use SIT; only the two exact local names are local (BR-03, BR-04).
- `[derived]` The SIT owner's user ID signed in on a production address is never `owner` there, and vice versa (BR-09).
- `[derived]` One environment filled and the other still the placeholder: the filled one works for its owner, the unfilled one refuses everyone (BR-10, BR-11a).
- `[derived]` A page opened on one address and then on another in the same browser picks the project again (BR-06).
- `[derived]` The production database is in Datastore mode until the owner moves it: a production save shows the existing failure message (Assumption 12; not testable here).
- `[derived]` The `develop` job must not use the production script, and the production job must not use the SIT script (BR-16c, BR-17c).

### 1.6 Out of scope

A tool to copy content between SIT and production; changing the production database mode; a visible environment label in the panel; any new screen, stored data, dependency or environment variable; restricting each API key to its own addresses in the cloud console; automating a real Google sign-in; filling in the two owner IDs; deleting the repo-level `FIREBASE_SERVICE_ACCOUNT` secret; treating `thegoldenpothos.dev` as production (all from the story).

## 2. Technical specification — SA

### 2.1 Approach

`src/lib/firebase/config.ts` becomes the single place that knows the three targets. It exports the three web configs, the two listed production addresses lists, the two local names, and two pure functions: `environmentFor(hostname)`, which is exact-match with SIT as the default, and `webConfigFor(hostname)`. `client.ts` starts the one Firebase app with `webConfigFor(window.location.hostname)`; Auth, Firestore and Storage are all built from that app, so one choice serves all three. `owner.ts` keeps one owner ID per environment and `ownerUidFor(hostname)` picks the right one; `accessFor` is unchanged. Both rules files get two owner functions (production first) behind one `isOwner()` that accepts either. The `develop` job gains the same credential and rules steps the `master` job has, with a new `deploy:rules:sit` script that names the SIT project explicitly. Five existing guard tests are rewritten to the new rules, and the feature's own spec observes the sign-in request per address with a stubbed Google script loader, the local stand-ins with a recorded request list, and the rules on the emulator.

### 2.6 Non-functional notes

- One owner, two environments: no concurrency, scale or multi-user concern (intent §8).
- Static export and `trailingSlash` are untouched; no `process.env`; no server.
- The Firebase web config is public by design; keys appear in `config.ts` only.
- Public pages load no Firebase code: no module outside the admin folders imports `src/lib/firebase` or `src/lib/admin`.
- Source in `src/lib/firebase/` and `src/lib/admin/` must contain neither the word "email" (E2E-15 of `admin-sign-in.spec.ts`) nor `process.env` (its E2E-16), and the rules files must contain neither (rule rows in two other specs).
- Styling is not touched, so the CSS-token rule is not in play.
