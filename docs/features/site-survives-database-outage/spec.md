## 1. Business analysis — BA

### 1.1 Purpose

The owner's site is the owner's professional face. When the Supabase project pauses or cannot be reached, a recruiter or reader must meet the same pages as before, never an error page or a blank section. The five landing-page sections and every blog page already keep the last good copy; this feature makes that true in the case the earlier slices left open: a Publish that succeeds, followed by an outage before the first visitor has caused the renewed page to be made. It also proves, with the database switched off, that every public page, the feeds, a draft, a saved-but-unpublished change, a failed Publish and a mistyped blog address behave as the story says.

### 1.2 Actors & preconditions

- Visitor and reader: not signed in; opens public pages, the RSS feed and the sitemap.
- Owner: signed in as the owner; presses Publish in the panel.
- Precondition for every scenario: the owner has published content (the fixtures of Section 4) and the database cannot be reached ("unreachable" per story assumption 1: no answer, paused, refused, or an answer that is an error).

## 2. Technical specification — SA

### 2.1 Approach

Today a successful Publish expires the landing page and the blog pages at once (`revalidatePath` and `revalidateTag(tag, { expire: 0 })`); the next visit must make a new copy, and if the database is down then, every visit answers 500 (impact.md SF-2, proven). The fix is to renew with stale-while-revalidate: every public read goes through one kept read (`unstable_cache` entries tagged per environment), and Publish marks that tag stale with `revalidateTag(tag, "max")`. The previous copy keeps serving while the framework makes the new one, and if making it fails the previous copy stays (SF-1, SF-3, proven in a throwaway app with the installed Next). Pages built without the database setting (the test flow) carry the tag of an empty setting, so Publish marks that one too (SF-4). A new module `src/lib/server/keptRead.ts` holds the kept read and the refresh; the five landing loaders and the posts loader call it; Publish calls `refreshPublishedSite()` after its existing owner check and profile read and no longer calls `revalidatePath`. The not-found page gains a link back to the blog. Three earlier source-reading tests and the standing documents are amended. The new spec switches the stand-in database off and checks every story scenario and the two derived cases.

export function keptRead<T>(name: string, read: () => Promise<T>, valueWithoutSetting: T): Promise<T>;

`T` must survive a JSON round trip (the cache stores JSON): the public view types hold strings, numbers, booleans, `null`, arrays and plain objects only.

## 4. Verification mapping — SA

Definitions used by the rows (the test file writes small helpers for them; earlier specs have the same shapes):

- `OWNER` cookie: the `authjs.session-token` session cookie for `ADMIN_EMAIL`, built as the earlier specs' `cookieOf(OWNER())` does. Owner requests use `/api/admin/*` addresses with their trailing slash.
- BREAK: write the stand-in file named by the text after `stand-in:` in `SUPABASE_DB_URL` with the key `"unreachable": true` added to its existing content. FIX: write it back without that key.
- BLANK: delete the stand-in file; owner `POST /api/admin/publish/` → 200 `{ "published": true }`; poll `GET /` (up to 60 s) until its text lacks `id="hero"`; poll `GET /blog/` until its text contains "No posts yet — check back soon!".
- FULL (the published fixture): BLANK; then, as the owner, `PUT /api/admin/profile/` with `{ "name": "Avery Quinn", "headline": "Platform Engineer", "about": ["Builds calm systems."], "photo": "", "email": "avery@example.com", "resumeLink": "", "socialLinks": [{ "label": "GitHub", "url": "https://github.com/avery-q" }] }`; `POST /api/admin/experience/` with `{ "position": 0, "content": { "year": "2026", "title": "Staff Engineer", "company": "Northwind Ltd", "duration": "Jan 2026 - Present", "description": "Leads the platform team.", "details": [] } }`; `POST /api/admin/tech-stack/` with `{ "position": 0, "content": { "category": "Languages", "tools": [{ "name": "TypeScript", "icon": "/icons/ts.png" }] } }`; `POST /api/admin/projects/` with `{ "position": 0, "content": { "title": "Lantern Notes", "shortDesc": "A notes app", "description": ["Built for fast capture."], "tech": ["React"], "github": "https://github.com/example/lantern", "demo": "" } }` (keep the returned `id` as `PROJECT_ID`); `POST /api/admin/certifications/` with `{ "position": 0, "content": { "name": "Certified Cloud Practitioner", "icon": "/certs/cloud.png", "url": "https://example.com/cert/cloud" } }`; `POST /api/admin/blog-posts/` twice with `{ "content": { "title": "Hello World", "excerpt": "A first post", "date": "2026-05-15", "slug": "hello-world", "tags": [], "draft": false, "featured": false, "coverImage": "", "coverAlt": "", "body": "Hello body words here.\n" } }` and `{ "content": { "title": "Second Outage Post", "excerpt": "A second excerpt", "date": "2026-06-01", "slug": "second-outage-post", "tags": [], "draft": false, "featured": false, "coverImage": "", "coverAlt": "", "body": "Second body words.\n" } }`; owner `POST /api/admin/publish/` → 200 `{ "published": true }`. The warm phase never opens a post's own address.
- RENEW: owner `POST /api/admin/publish/` → 200 `{ "published": true }`, then nothing is visited before BREAK.
- Test-writing rules (from the earlier slices' gate findings): the new spec file contains no text naming the retired backend provider (an earlier acceptance check scans every spec for it); alerts are located by their expected text, never by role alone; the file names no `manual` row; every Verify command below is literal; the earlier specs are amended minimally and named by title, never by id.
